# TEST_PLAN — 테스트 계획

> 기준 v10.0 · 2026-11-14 · 상태: v6.0까지의 클라이언트 테스트(EditMode 198개, PlayMode 15개)는 Unity 에디터에서 통과한 기록이 있음 (3.1, 3.2장). **v8.0은 Unity가 없는 PC에서 작업해 Unity 에디터의 테스트를 한 번도 돌리지 못함.** 대신 규칙 테스트 272개(.NET), Unity 코드 형식 검사, 서버 테스트 133개(PHP + 테스트 DB)를 돌려 모두 통과 (13장). 실제 게임 화면에서의 v8.0 동작, 빌드된 실행 파일, 사람이 해 보는 테스트는 없음. **v7.0 현실 혜택(CITY PASS · SCHOLARSHIP)도 같은 PC에서 작업함: 규칙 테스트 329개, 서버 테스트 215개 통과, Unity 코드는 형식 검사만. 브라우저·실제 기기·QR 촬영·동시 요청은 확인하지 못함 (14장)** **v9.0(도시 성장, 협동 방어전, 미니맵, 지방세)도 같은 PC에서 작업함: 규칙 테스트 385개, 서버 테스트 302개, 실시간 서버 테스트 39개 통과, 게임 서버와 실시간 서버를 실제로 띄워 두 접속으로 한 판을 돌린 확인 47개 통과. Unity 코드는 형식 검사만 했고 협동 방어전 화면과 미니맵을 눈으로 본 적이 없음 (15장)** **v10.0(실시간 3종 대시보드)도 같은 PC에서 작업함: 규칙 테스트 415개, 서버 테스트 310개, 실시간 서버 테스트 39개 통과, 게임 서버를 띄워 요약 API 를 HTTP 로 확인 29개 통과. 카드의 자리 잡기는 해상도 11가지를 계산으로 확인. Unity 코드는 형식 검사만 했고 카드의 모양·움직임을 눈으로 본 적이 없으며 PlayMode 테스트 2개는 실행하지 못함 (16장)**

## 1. 원칙

- 돈과 인증에 관련된 코드는 자동 테스트 없이 배포하지 않습니다.
- 규칙(계산식, 상태 기계)은 화면 없이 테스트할 수 있게 분리해 작성합니다.
- "동작한다"는 직접 실행해 확인한 것만 말합니다.
- 재미와 쉬움은 자동 테스트로 알 수 없으므로 사람이 해 보는 테스트를 단계마다 합니다.

- 다음 날 이자 예약 작업 뒤 통장에 이자가 들어오고 원장에 `bank_interest`가 남는다.
- 12단계에서 "나중에"를 고른 경우에도 15단계를 제외한 나머지가 진행된다 (은행 이용 조건에 따라).

### 3.1 지금 자동으로 확인되는 범위 (2026-11-13)

17단계가 모두 클라이언트에 구현되어 있고, 단계마다 자동 테스트가 있습니다. 다만 **위 점검표의 조건("Windows 빌드에서, 서버에 연결한 상태로, 처음부터 끝까지 한 번에")은 아직 한 번도 충족하지 못했습니다.** 아래 테스트는 Unity 에디터의 PlayMode에서, 서버 대신 `LocalMockBackend`로, 흐름별로 나뉘어 돕니다.

| 단계 | 자동 테스트 (PlayMode) | 자동 테스트가 보지 못하는 것 |
|---|---|---|
| 1 | — | 실행 파일로 시작하는 것 (빌드가 만들어지는 것만 확인) |
| 2~7 | `FirstPlayTests` | |

테스트 준비를 위해 건너뛰는 곳: 상점·은행 테스트는 돈을 모의 서버에 사냥 보고를 직접 보내 마련하고, 방어전·지도·상점·은행 테스트는 튜토리얼을 마친 상태에서 시작합니다. 17단계를 한 사람이 한 번에 이어서 하는 테스트는 없습니다.

### 3.2 17단계 밖의 것: Phase 3의 나머지 (2026-11-13)

| 기능 | EditMode (규칙과 모의 서버) | PlayMode (걸어가서 키로) | 자동 테스트가 보지 못하는 것 |
|---|---|---|---|

PlayMode 전체(15개)는 한 번에 약 6분, EditMode 전체(198개)는 약 30초 걸립니다.

한 번 실패한 뒤 고친 테스트 (2026-11-13): `ShopTests`의 "겨눌 적이 없으면 조준 표시가 없다"가 전체 실행에서 한 번 실패했습니다. 조준 표시는 프레임의 끝(LateUpdate)에 갱신되는데, 테스트가 전투 구역에서 광장으로 순간 이동한 바로 그 프레임에 표시를 확인하고 있었습니다. 게임의 동작은 바꾸지 않고, 테스트가 한 프레임 뒤에 확인하게 했습니다. 순간 이동은 테스트만 하는 일입니다.

## 4. 금융 거래 검증

### 4.1 정확성

| 항목 | 확인 |
|---|---|
| 구매 | 잔액 차감과 아이템 지급이 함께 일어나거나 함께 취소된다 |
| 잔액 부족 | 거절되고 아무것도 바뀌지 않는다 |
| 입출금 | 지갑과 통장의 합이 변하지 않는다 |
| 이자 | 최저 잔액 기준, 한도 적용, 1 GC 미만 버림 |
| 이자 중복 | 예약 작업을 두 번 돌려도 하루치만 지급된다 |
| 이자 누락 | 작업이 며칠 빠진 뒤 돌려도 빠진 날짜만큼 정확히 지급된다 |
| 음수 | 어떤 요청으로도 잔액이 음수가 되지 않는다 |
| 큰 수 | 한도 근처의 금액에서 넘침이 없다 |

### 4.2 동시성과 재전송

| 항목 | 확인 |
|---|---|
| 동시 구매 | 잔액 200으로 200짜리 구매를 동시에 10건 → 1건만 성공 |
| 동시 입출금 | 동시에 입금과 출금을 섞어 보내도 합계가 맞는다 |
| 같은 키 재전송 | 같은 중복 방지 키 → 한 번만 처리, 같은 응답 |
| 같은 키 다른 내용 | 거절 |
| 응답 유실 | 서버는 처리했지만 클라이언트가 응답을 못 받은 경우, 재전송으로 같은 결과 |
| 교착 | 반대 순서의 동시 요청에서 멈추지 않는다 |

### 4.3 정합성

- 매 테스트 뒤 "지갑 잔액 = 마지막 원장 잔액"과 "계정별 원장 합 = 잔액"을 검사한다.
- 무작위 거래를 대량으로 실행한 뒤에도 성립하는지 확인한다.

### 4.4 Phase 4 추가

| 항목 | 확인 |
|---|---|
| 주식 손익 | 여러 번 나눠 사고판 뒤 취득원가, 실현손익, 평가손익이 손 계산과 일치 |

## 5. 데이터 저장과 복구

| 항목 | 확인 |
|---|---|
| 정상 종료 후 재실행 | 3장의 17 |
| 강제 종료 | 작업 관리자로 종료한 뒤 재실행. 마지막 서버 응답까지의 상태가 남아 있다 |
| 전투 중 종료 | 진행 중이던 전투는 무효. 보상 없음, 재화 손실 없음 |

### 15.5 두 서버를 실제로 띄운 확인 (2026-11-14)

빈 DB 에 마이그레이션 0001~0011을 적용하고, PHP 내장 웹 서버(`127.0.0.1:8319`)와 실시간 서버(`127.0.0.1:8390`)를 띄운 뒤, 스크립트가 HTTP 와 WebSocket 접속 두 개로 확인했습니다. 서명 키는 그 자리에서 만든 무작위 값을 환경변수로만 주었습니다. 47개 모두 통과.

| 단계 | 확인한 것 |
|---|---|
| 올린 직후 (아무것도 켜지 않음) | 버전 `9.0.0`. v9.0 경로 9개가 토큰 없이는 401. 게스트 두 명이 전입해도 유효 전입자 0. 세금 3종이 꺼져 있음. 재정·집행 내역·참여예산 선택지가 열림. 참여예산 제안은 403. 협동 방어전은 `available: false`(`coop_disabled`), 만들기는 403. 내부 경로는 서명이 없거나 틀리면 404 |
| 협동 방어전을 켠 뒤 | 만들기 → 참여 → 입장권 두 장 → **두 접속이 실시간 서버에 입장** (실시간 서버가 게임 서버에서 판 설정을 받아 옴) → 쓴 입장권은 다시 못 씀 → 방장이 아니면 시작 못 함 → 방장이 시작 (게임 서버의 판이 `running`) → **두 접속이 같은 자리에 동시에 설치: 하나만 성공, 하나는 `slot_taken`** → 같은 요청을 다시 보내도 한 번만 차감 → 핑이 상대에게 전달 → 연달아 보낸 핑은 `ping_rate` → 한 사람의 이동이 상대의 상태에 반영 → 상태에 적·타워·관문·공동 예산 |
| 모두 나간 뒤 | 1분 뒤 패배로 닫힘 → **실시간 서버가 결과를 게임 서버에 보고** → 결과·공동 예산 장부·내 기록이 REST 로 보임 (조금만 참여해 보상 없음 `low_participation`) → 실시간 서버의 방이 치워짐 → `bin/tick.php`의 점검에 문제 없음 |

### 16.3 해상도별 UI 테스트 (계산)

화면을 띄울 수 없어 **자리 잡기 규칙을 계산으로** 확인했습니다 (`Layout_KeepsItsPromises_AtEveryResolutionScaleAndHudSituation`). 자세한 축과 조건은 [HUD_LAYOUT_SYSTEM](HUD_LAYOUT_SYSTEM.md) 7장.

| | |
|---|---|
| 해상도 | 1280×720, 1366×768, 1600×900, **1920×1080**, 2560×1440, 3840×2160, 2560×1080, 3440×1440, 1920×1200, 1280×1024, 1024×768 |
| × 배율 | 80, 100, 120, 140% |
| × 다른 HUD 가 쓰는 자리 | 6가지 (평소부터 협동 방어전, 거의 다 찬 화면까지) |
| × 카드 상태 | 5가지 |
| × 기둥 | 오른쪽, 왼쪽 |
| 합계 | **2,640가지 모두 통과** |

지켜지는 것: 폭 ≤ 화면의 24%, 화면 밖으로 나가지 않음, 카드끼리 겹치지 않음, 다른 HUD 의 자리를 침범하지 않음, 숨긴 카드는 나타나지 않고 숨기지 않은 카드는 사라지지 않음, 접어 둔 카드가 저절로 펴지지 않음.

그 밖에: 1920×1080에서의 자리(`Layout_At1080p_StacksCardsOnTheRightBelowTheWallet`), 접히는 순서(`Layout_CollapsesCardsInOrder_…`), 한 줄로 줄어들기(`Layout_PutsThreeCardsInOneRow_…`), 화면이 재는 기둥과 규칙의 기둥이 같음(`Layout_ColumnIsTheSameOneTheCardsUse`).

**이것은 계산입니다.** 실제 화면에서 글자가 칸을 넘는지, 다른 HUD 를 잰 값이 맞는지, 4K 에서 선명한지는 확인하지 못했습니다 (16.6).
