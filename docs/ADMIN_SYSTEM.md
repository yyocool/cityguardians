# ADMIN_SYSTEM — 웹 관리자

> 기준 v10.0 · 2026-11-14 · 상태: v8.0의 전투·도시 위험도 메뉴 13개와 로그인·2단계 인증·역할·변경 이력·감사 기록(10장), v7.0의 현실 혜택 기능 승인·CITY PASS·장학 메뉴 13개와 업무별 역할 5개(11장), v9.0의 도시 성장·모델링·협동 방어전·지방세·재정·참여예산 메뉴 9개와 역할 1개(12장), v10.0의 실시간 대시보드 설정 메뉴 1개(13장)를 구현하고 **로컬에서만** 검증함. **운영 서버에는 올리지 않음.** 플레이어·제재·공지·금융 메뉴(4장의 v6.0 목록)는 설계만 있음

## 0. 현황

운영 서버의 `/admin` 경로는 404를 돌려줍니다. 관리자 화면이 아직 없거나 다른 경로에 있는 것으로 보이며, 서버 소스 확인 뒤 판단합니다. 기존 관리자가 있으면 그 위에 메뉴를 더하는 방향으로 진행합니다.

v8.0에서 이 저장소의 `server/` 안에 관리자 화면을 만들었습니다 (`server/src/Admin/`). 게임 API와 같은 애플리케이션이고 경로만 `/admin`으로 다릅니다. 운영 서버에 기존 관리자가 있는지는 여전히 확인하지 못했으므로, 올리기 전에 경로가 겹치는지 먼저 확인해야 합니다.

## 1. 목적

- 경제 수치와 게임 밸런스를 코드 배포 없이 바꿉니다.
- 플레이어와 금융 거래를 조회하고 문제를 처리합니다.
- 신고를 처리하고 제재합니다.
- 홈페이지 공지와 다운로드 빌드를 관리합니다.

## 2. 접근과 보안

| 항목 | 내용 |
|---|---|
| 기술 | PHP, MySQL. 게임 API와 같은 애플리케이션 안의 별도 영역 |
| 경로 | 게임 API와 분리된 경로 |
| 계정 | 플레이어 계정과 별개의 `admins` 테이블 |
| 비밀번호 | 강한 해시로 저장. 최소 길이와 복잡도 규칙 |
| 2단계 인증 | 일회용 코드 앱(TOTP) 필수 |
| 세션 | 쿠키에 Secure, HttpOnly, SameSite=Strict. 일정 시간 조작이 없으면 만료 |
| 요청 위조 방지 | 모든 변경 요청에 CSRF 토큰 |
| 로그인 시도 제한 | 연속 실패 시 일시 잠금 |
| 접속 IP 제한 | 허용 목록 (선택. 설정 가능하게) |
| 감사 기록 | 모든 변경과 민감한 조회를 `admin_audit_logs`에 기록 |
| 검색 엔진 | 색인 금지 |

첫 관리자 계정은 서버에서 명령행 도구로 만듭니다. 웹에서 가입하는 기능은 두지 않습니다.

## 3. 역할

| 역할 | 할 수 있는 일 |
|---|---|
| 최고 관리자 | 전부. 관리자 계정 관리 |
| 운영자 | 플레이어, 제재, 신고, 공지, 수동 잔액 조정 |
| 밸런스 담당 | 적, 타워, 아이템, 상점, 스테이지, 금융 상품, 정책 수정 |
| 고객지원 | 플레이어 조회, 신고 처리, 채팅 제재 |
| 조회 전용 | 대시보드와 목록 조회 |

수동 잔액 조정처럼 영향이 큰 작업은 사유 입력을 필수로 하고, 일정 금액을 넘으면 최고 관리자만 할 수 있게 합니다.

## 5. 운영 대시보드

| 묶음 | 지표 |
|---|---|
| 이용 | 오늘 접속자, 신규 게스트, 전입신고 수, 이방인 → 주민 전환율 |
| 진행 | 첫 플레이 단계별 이탈 (방 → 도시 → 첫 전투 → 첫 구매 → 첫 방어전) |
| 경제 | 오늘 발행 GC, 회수 GC, 총 유통량, 예금 총액 |
| 금융 | 대출 총액, 연체율, 주식 거래량 (Phase 4) |
| 안전 | 미처리 신고 수, 오늘 제재 수, 거절된 보상 보고 수 |
| 상태 | 예약 작업의 마지막 성공 시각, 원장 정합성 점검 결과, 최근 오류 |

"첫 플레이 단계별 이탈"은 재미를 확인하는 가장 중요한 지표입니다. 어디서 그만두는지 보이면 무엇을 고칠지 알 수 있습니다.

## 6. 밸런스 수정 절차

1. 메뉴에서 값을 고칩니다.
2. 서버가 범위를 검사합니다 (음수 가격, 0 이하의 체력, 지나치게 높은 이율 등은 거부).
3. 변경 사유를 적고 저장합니다.
4. 변경 전후 값, 관리자, 사유가 `config_history`에 남습니다.
5. 정의 데이터 버전이 올라가고, 클라이언트는 다음 접속 때 새 정의를 받습니다.
6. 이력에서 이전 값으로 되돌릴 수 있습니다.

금융 조건을 바꿔도 이미 맺은 계약(정기예금의 약정 이율, 실행된 대출의 이율과 기한)은 바뀌지 않습니다.

스테이징 환경에서 먼저 값을 시험할 수 있도록 정의 데이터를 내보내고 가져오는 기능을 둡니다.

## 7. 플레이어 조회와 조치

| 조치 | 조건 |
|---|---|
| 조회 | 고객지원 이상. 조회 기록을 남김 |
| 이용 정지·해제 | 운영자 이상. 사유와 기간 필수 |
| 닉네임 강제 변경 | 운영자 이상 |
| GC 수동 조정 | 운영자 이상. 원장에 `admin_adjust`, 사유 필수 |
| 아이템 지급·회수 | 운영자 이상. 기록 필수 |
| 계정 삭제 요청 처리 | 최고 관리자. 절차는 [SECURITY_POLICY](SECURITY_POLICY.md) 8장 |

관리자는 플레이어의 게스트 비밀키나 접속 토큰을 볼 수 없습니다 (해시만 저장).

## 8. 화면 구성

- 왼쪽 메뉴, 오른쪽 내용의 단순한 구성. PC 화면 기준.
- 목록은 검색, 정렬, 쪽 나눔을 공통으로 제공합니다.
- 외부 스크립트·글꼴을 불러오지 않습니다 (운영 사이트의 콘텐츠 보안 정책과 같은 방침).
- 모든 화면 출력은 이스케이프합니다. 플레이어가 입력한 닉네임과 채팅이 관리자 화면에서 스크립트로 실행되어서는 안 됩니다.

첫 화면(`/admin`)은 단계별 도시 수, 진행 중인 침공, 열려 있는 지원 요청, 최근 24시간의 전투 수·거절된 보고·서버 오류, 마지막 침공 판정 시각을 보여 줍니다.

위험 단계는 관리자 화면에서도 색과 함께 모양과 글자로 표시합니다.

### 10.2 역할

| 역할 | 보기 | 정의·정책·가중치 수정 | 위험도 조정, 침공 시작·종료, 모드 여닫기 | 감사 기록 |
|---|---|---|---|---|
| 최고 관리자 `super` | ○ | ○ | ○ | ○ |
| 운영자 `operator` | ○ | × | ○ | ○ |
| 밸런스 담당 `balance` | ○ | ○ | × | × |
| 고객지원 `support` | ○ | × | × | × |
| 조회 전용 `viewer` | ○ | × | × | × |

권한이 없는 역할에는 폼이 보이지 않고, 요청을 직접 보내도 403으로 거절합니다 (화면과 서버 두 곳에서 확인).

### 10.3 보안 (2장의 항목을 어떻게 구현했는가)

| 항목 | 구현 |
|---|---|
| 계정 | `admins` 테이블. 플레이어 계정과 무관. 웹에서 만들 수 없음 |
| 비밀번호 | `password_hash()`. 12자 이상, 대문자·소문자·숫자·기호 가운데 세 가지 이상 |
| 2단계 인증 | TOTP(6자리, 30초, 앞뒤 한 칸 허용) **필수**. 같은 코드는 두 번 받지 않음 (`totp_last_step`) |
| 세션 | 무작위 토큰의 해시만 DB에 저장. 쿠키 `cg_admin`: `HttpOnly`, `SameSite=Strict`, `Secure`(기본), 경로 `/admin`. 조작이 없으면 30분, 길어도 12시간에 끝남 |
| 요청 위조 방지 | 값을 바꾸는 요청은 POST뿐. 모두 CSRF 토큰 확인 + `Origin` 확인. 거절은 감사 기록에 남음 |
| 로그인 시도 제한 | 계정: 5번 틀리면 15분 잠금. 주소: 10분에 10번 (`ADMIN_LOGIN_PER_10MIN`). 실패 이유를 구분해 알려 주지 않음 |
| 접속 IP 제한 | `ADMIN_ALLOW_IPS`. 목록 밖에서는 404 |
| 감사 기록 | 로그인·실패·로그아웃·모든 변경·거절된 요청을 `admin_audit_logs`에 기록 |
| 검색 엔진 | `X-Robots-Tag: noindex, nofollow` + `<meta name="robots">` |
| 응답 헤더 | `Content-Security-Policy: default-src 'none'; style-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store` |
| 스크립트 | **자바스크립트를 쓰지 않음.** 외부 스크립트·글꼴 없음. 스타일은 `assets/admin.css` 하나 |
| 출력 | 모든 값을 `Html::e()`로 이스케이프. 닉네임·사유에 넣은 태그가 실행되지 않는 것을 테스트로 확인 |
| 오류 | 내부 정보는 화면에 내보내지 않고 `system_logs`에만 남김 |

첫 관리자는 서버에서 만듭니다.

```
php server/bin/create-admin.php <아이디> <역할>
```

비밀번호는 물어봅니다 (명령행 인자로 받지 않습니다). TOTP 비밀값은 이때 한 번만 보여 줍니다.

### 10.4 밸런스 수정 (6장의 절차)

| 6장의 단계 | 구현 |
|---|---|
| 범위 검사 | 항목마다 최소·최대가 정해져 있고 폼에 범위를 보여 줌. 벗어나면 저장하지 않고 이유를 보여 줌. 묶음 검사도 함: 단계 경계의 순서(주의 < 위험 < 긴급), 지원 요청이 닫히는 값 ≤ 열리는 값, 위험도를 올리는 사건의 가중치는 0 이상·내리는 사건은 0 이하, 랭킹 가중치의 합 > 0, 웨이브·적 묶음 JSON의 형식과 적 코드 |
| 사유 | 필수 (2~255자) |
| 이력 | 정의·설정은 `config_history`에 바뀐 항목의 전후 값, 관리자, 사유. 위험도 정책은 `city_risk_policy`에 새 행 |
| 되돌리기 | 변경 이력과 지난 정책에서. 되돌리는 것도 새 이력으로 남음 |
| 반영 | 서버는 다음 요청부터 새 값을 씀. `GET /defs`의 `version`이 바뀜 |
| 내보내기·가져오기 | **없음** |

보상 금액은 서버가 정의에서 계산하므로, 여기서 고친 값이 곧 지급되는 값입니다. 진행 중인 전투는 시작할 때의 정의가 아니라 **끝날 때의 정의**로 계산됩니다 (전투 중에 보상을 고치면 그 판부터 바뀝니다).

### 10.5 한계

- **고치기만 됩니다.** 적·타워·장비·구역·임무를 새로 더하거나 지우는 화면이 없습니다 (새 적과 타워는 클라이언트의 모델이 함께 있어야 합니다. 끄려면 "사용"을 끕니다). 코드, 종류, 소유 방식, 장비의 칸, 전투 모드의 시점(`camera`), 사냥 구역에 나오는 적은 보여 주기만 합니다.
- 웨이브 구성과 FPS의 적 묶음은 JSON 글자를 직접 고치는 방식입니다 (형식은 검사하지만 편집 화면이 따로 없습니다).
- 범위는 "게임이 망가지지 않는 한도"입니다. 알맞은 값인지는 검사하지 않습니다 (예: 보상을 10만 GC로 올릴 수 있습니다).
- 4장의 v6.0 메뉴 가운데 플레이어, 전입신고, 아이템, 상점, 금융자산, 은행, 제재, 공지, 시스템 로그 화면이 없습니다. GC 수동 조정 화면도 없습니다.
- 관리자 계정을 화면에서 관리할 수 없습니다 (명령줄로 만들기만 됨. 비밀번호 변경·비활성화는 DB에서 직접).
- 목록의 정렬과 쪽 나눔이 없습니다 (도시 위험도는 시·도로 걸러 보기, 나머지는 최근 N건).
- 테스트 28개는 관리자 처리기를 직접 부르는 방식과 PHP 내장 웹 서버로 확인했습니다. Apache / nginx 위에서는 돌려 보지 않았습니다.

### 11.2 현실 혜택 기능 승인

`/admin/benefits`. 현실 혜택을 주는 기능 넷은 **꺼진 채로, "검토 전" 상태로** 설치됩니다.

| 코드 | 기능 | 꺼져 있을 때 |
|---|---|---|
| `city_pass_membership` | CITY PASS 멤버십 가입 | 가입할 수 없음 |
| `city_pass_coupons` | 쿠폰 발급과 사용 | 제휴 상점·혜택이 밖에 보이지 않음. 쿠폰을 받거나 쓸 수 없음. 멤버십이 켜져 있어야 켤 수 있음 |
| `scholarship_applications` | 장학 신청 접수 | 공고가 보이지 않음. 공고를 낼 수 없음. 신청할 수 없음. 암호화 키(`DATA_KEY`)가 있어야 켤 수 있음 |
| `scholarship_awards` | 선정 결과와 지급 상태 | 최종 승인, 결과 통지, 지급 기록을 할 수 없음 |

켜는 절차:

1. **법률 검토 결과를 기록합니다** (준법 담당 또는 최고 관리자). 상태(검토 전 / 검토 중 / 검토 완료 / 반려)와 사유. "검토 완료"로 기록하려면 **검토 의견서의 문서 번호, 검토한 곳, 검토한 날짜**가 모두 있어야 합니다.
2. **다른 최고 관리자가 켭니다.** 법률 검토 완료를 기록한 사람은 그 기능을 켤 수 없습니다. 사유 필수.
3. 모든 기록·켜기·끄기는 `benefit_feature_history`(전후 값, 관리자, 사유)와 `admin_audit_logs`에 남습니다.

안전장치:

- 검토 상태가 "검토 완료"가 아니게 되면 그 기능은 **자동으로 꺼집니다.**
- DB 의 `is_enabled`를 직접 1로 고쳐도, 법률 검토가 완료로 기록되어 있지 않으면 서버는 꺼진 것으로 봅니다.
- 끄기는 준법 담당과 최고 관리자가 언제든 할 수 있습니다.
- 서버 설정 `BENEFITS_LOCKED=1`이면 관리자 화면의 상태와 관계없이 넷 다 꺼집니다 (비상용).
- 화면 아래에 **만들지 않은 기능** 다섯 가지를 보여 줍니다 (GC ↔ 현실 상품 교환, 전투 성적에 따른 현금성 보상, 랭킹에 따른 장학금 자동 지급, 유료 구매에 따른 장학 가산점, 게임 내 대출·주식 수익의 현금화). 이것들은 스위치가 없습니다 — 코드가 없습니다.

이 화면은 "법률 검토가 끝났다는 기록"을 확인할 뿐이고, 검토 자체를 대신하지 않습니다. 기록의 진위는 사람이 책임집니다.

### 11.4 같은 사람이 만들고 승인할 수 없는 일

| 일 | 할 수 없는 사람 |
|---|---|
| 현실 혜택 기능 켜기 | 그 기능의 법률 검토 완료를 기록한 사람 |
| 제휴 업체 승인 | 그 업체를 등록하거나 마지막으로 고친 사람 |
| 혜택 승인 | 그 혜택을 등록하거나 마지막으로 고친 사람 |
| 장학 공고 승인 | 그 프로그램을 작성하거나 마지막으로 고친 사람 (자격·평가 기준을 고친 것 포함) |
| 선정 최종 승인 | 선정을 제안한 사람 |
| 이의신청 처리 | 원래 결정을 내린 사람 (자격 미해당이면 자격을 확인한 사람, 선정 결과이면 선정을 제안한 사람). 최종 승인만 한 사람은 막지 않음 |
| 지급 기록 승인 | 그 기록을 만든 사람 |

서버가 계정 번호로 확인합니다. 한 사람이 계정 두 개를 갖는 것은 기술로 막을 수 없습니다 — 계정 발급 절차로 막아야 합니다.

### 11.5 그 밖에 지켜지는 것

- 모든 상태 전환과 결정에 **사유가 필수**입니다.
- 제휴 업체를 승인하려면 계약서의 문서 번호, 끝나지 않은 계약 기간, 청소년에게 맞지 않는 업종이 아니라는 확인, 사용 중인 지점이 하나 이상 있어야 합니다. 승인되지 않은 업체와 혜택은 게임·홈페이지 어디에도 나오지 않습니다.
- 혜택의 발급 근거는 "CITY PASS 가입 / 무료 프로모션 / 제휴사가 공개한 조건" 셋뿐입니다. GC·전투 성적을 조건으로 하는 값이 없습니다.
- 장학의 자격 종류는 넷뿐이고, 평가 기준의 이름에 게임 성적·게임머니·랭킹·결제를 뜻하는 말이 있으면 거절합니다.
- 상점 계정의 임시 비밀번호는 만들 때 한 번만 화면에 나옵니다. 해시만 저장합니다.
- 쿠폰·사용 내역 화면에서 회원은 회원번호로만 보입니다. 닉네임과 계정 번호는 나오지 않습니다.
- 지급 화면에는 계좌번호를 넣는 칸이 없고, 송금 기능이 없습니다.

### 11.6 한계

- 관리자 계정을 화면에서 관리할 수 없는 것은 10.5와 같습니다. 역할을 바꾸려면 DB 에서 직접 고쳐야 합니다.
- 한 계정에 역할이 하나라서, 작은 조직에서는 계정이 여러 개 필요합니다 (11.4의 분리 때문에 장학을 돌리려면 적어도 장학 담당 둘, 심사위원 둘, 지급 담당 둘 — 또는 최고 관리자가 한쪽을 맡음).
- 부정 사용 탐지는 화면에 신호를 보여 줄 뿐입니다. 알림(메일·메신저)과 자동 차단이 없습니다.
- 통계를 파일로 내보내는 기능이 없습니다.
- 지점의 대표 이미지는 파일 이름만 적습니다 (파일은 서버의 `public/media`에 따로 올려야 함). 올리기 화면이 없습니다.
- 테스트(`BenefitAdminTest` 6개와 서비스 테스트)는 관리자 처리기를 직접 부르는 방식입니다. 실제 브라우저와 Apache / nginx 위에서는 돌려 보지 않았습니다.

| 설정 | `config.update` (`growth`, `coop`, `ping`, `treasury`, `budget`) |

정책·기준·설정의 변경은 바꾸기 전·후의 값이 `config_history`에도 남습니다. 플레이어가 한 일(이사, 제안, 투표, 납세)은 감사 기록이 아니라 각자의 기록 테이블과 원장에 남습니다.

**이전 값으로 되돌리기:** "변경 이력"(`/admin/history`)에서 세금 정책, 확장 기준, 한 도시만의 기준 인원, 팀 역할, 설정 5개의 이력마다 "이전 값으로" 단추가 보입니다 (`city.policy` 권한). 값을 직접 덮어쓰지 않고 **화면에서 고칠 때와 같은 저장 함수**를 거칩니다 (`CG\Service\CityOpsHistory`). 그래서 권한·범위 검증·사유가 똑같이 적용되고, 되돌린 것도 새 이력 한 줄(`되돌리기 #번호: 사유`)과 감사 기록으로 남습니다. 지금의 허용 범위를 벗어나는 옛 값으로는 돌아가지 않습니다.

### 12.6 한계

- 되돌릴 수 있는 것은 **정책·기준·설정의 값**입니다. 이미 일어난 일(걷은 세금, 집행한 예산, 배포한 콘텐츠, 닫은 판, 확정된 투표)은 되돌리기 단추가 없습니다. 콘텐츠는 철회로, 나머지는 따로 절차를 정해야 합니다.
- 알림은 화면에서만 보입니다. 담당자에게 따로 알려 주지 않습니다.
- 결과물 등록은 **경로와 해시를 적는 것**입니다. 파일을 올리는 화면이 없습니다 (콘텐츠 저장소에는 따로 올림).
- 협동 방어전의 "진행 중인 판"은 게임 서버가 아는 것(누가 들어가 있는가)만 보입니다. 전투 중의 상태(웨이브, 관문 내구도)는 실시간 서버에만 있어서 관리자 화면에 나오지 않습니다.
- 관리자가 닫은 판은 실시간 서버가 30초 안에 알아채고 방을 닫습니다. 바로 닫히지는 않습니다.
- 통계를 파일로 내보내는 기능, 그래프가 없습니다 (추이는 표로 보임).
- 테스트는 관리자 처리기를 직접 부르는 방식입니다. 실제 브라우저에서는 돌려 보지 않았습니다.

## 13. v10.0에서 구현한 것: 실시간 대시보드 설정

`server/src/Admin/DashboardPages.php`. 게임 화면 오른쪽의 카드 세 장([LIVE_DASHBOARD](LIVE_DASHBOARD.md))의 기본값을 정하는 화면 하나입니다. 로그인·2단계 인증·CSRF·접속 주소 제한·세션은 10.3 그대로이고, 권한도 v9.0의 것을 그대로 씁니다 (새 권한과 역할 없음). 테스트는 `server/tests/DashboardTest.php`의 관리자 부분 3개.

### 13.1 메뉴

| 메뉴 | 경로 | 보는 것 (`city.view`) | 할 수 있는 일 (`city.policy`) |
|---|---|---|---|
| 실시간 대시보드 설정 | `/admin/dashboard` | 지금의 설정, 카드가 보여 주는 값과 그 출처, 최근 변경 10건 | 설정 바꾸기 (`POST /admin/dashboard/settings`) |

지시서 10장의 항목과 설정:

| 지시서 | 설정 (`game_config`의 `dashboard`) | 범위 | 기본 |
|---|---|---|---|
| 카드별 기본 표시 여부 | `financeVisible`, `cityVisible`, `nationalVisible` | 표시 / 숨김 | 표시 |
| 기본 펼침 상태 | `financeExpanded`, `cityExpanded`, `nationalExpanded` | 펼침 / 접힘 | 펼침, 펼침, **접힘** |
| 데이터 갱신 간격 | `refreshSeconds` | 5 ~ 300초 | 20 |
| 도시 위험 경고 기준 | `cityAlertRisk` | 위험도 0 ~ 100 | 70 |
| 전국 긴급 알림 표시 정책 | `nationalNotice` | 표시 안 함 / 긴급 단계인 도시 / 긴급 단계이거나 침공 중인 도시 | 긴급 단계인 도시 |
| 〃 | `nationalNoticeMax` (한 번에 알리는 도시 수) | 1 ~ 10 | 3 |
| (지시서 14장: 준비되지 않은 기능의 표시) | `sampleData` | "준비 중"으로 표시 / "개발용 샘플"로 표시 | "준비 중" |

- **표시와 펼침은 처음 보는 이용자의 기본값**입니다. 이용자가 자기 화면에서 접거나 숨긴 것은 그 기기에 저장되고 이 값으로 덮어쓰지 않습니다. 화면에도 그렇게 적혀 있습니다.
- 바꾼 값은 요약 응답의 `settings`로 내려가고, 클라이언트는 **다음에 요약을 받을 때부터** 씁니다 (늦어도 이전 갱신 간격 뒤).
- 갱신 간격을 5초로 내리면 접속자 한 사람이 1분에 12번 요약을 받습니다. 요약 한 번은 전국 도시의 위험도와 랭킹을 읽으므로, 이용자가 많을 때 낮추려면 부하를 먼저 재야 합니다 (13.4).
- 경고 기준을 0 으로 두면 모든 주민의 카드에 "위험도가 높아요"가 뜹니다. 범위 안의 값이라 막지 않습니다.

### 13.2 지키는 것

| 규칙 | 구현 |
|---|---|
| 권한 | 보기 `city.view`, 바꾸기 `city.policy` (최고 관리자, 밸런스 담당). 화면에서 폼을 숨기고, 저장 함수(`Settings::save`)가 요청마다 다시 확인. v7.0의 업무별 역할은 이 화면을 볼 수 없음 |
| 변경 요청 | `POST`, CSRF 토큰, **사유 필수** |
| 범위 검증 | 항목마다 최소·최대. 벗어나면 저장하지 않고 어느 항목이 틀렸는지 보여 줌 (`422`). 고르는 값(표시/숨김 등)은 목록에 있는 값만 |
| 이력과 감사 | 바꾸기 전·후의 값이 `config_history`에, 행동이 `admin_audit_logs`(`config.update`, 대상 `game_config` / `dashboard`)에 남음. 바뀐 값이 없으면 남기지 않음 |
| 되돌리기 | "변경 이력"(`/admin/history`)의 "이전 값으로" — 같은 저장 함수를 거치므로 권한·범위·사유가 똑같이 적용되고, 되돌린 것도 이력 한 줄로 남음 (12.5와 같은 방식) |
| 출력 | 모두 `Html::e()`. 외부 스크립트·글꼴 없음 |

### 13.3 이용자의 금융 정보를 내보이지 않음

지시서 10장: "일반 이용자의 금융 정보는 관리자 화면에 불필요하게 노출하지 마세요."

- 이 화면은 **설정과 그 변경 이력만** 읽습니다 (`game_config`, `config_history`, `admins`). 지갑, 원장, 플레이어 테이블을 읽지 않습니다.
- 화면에 잔액, 거래 내역, 순자산, 계정 ID, 닉네임이 나오지 않습니다. "카드가 보여 주는 값과 그 출처" 표는 **값의 종류**를 설명할 뿐 누구의 값도 보여 주지 않습니다.
- 대시보드 요약을 관리자가 남의 것으로 받아 보는 기능("이 이용자의 화면 보기")을 만들지 않았습니다.
- 테스트(`DashboardTest::testAdminScreenShowsNoPlayerFinance`)가 큰 잔액이 있는 이용자를 만든 뒤, 최고 관리자·밸런스 담당·운영자 각각의 화면 HTML 에 그 금액(쉼표가 있는 것과 없는 것), 닉네임, 공개 ID 가 없는지 확인합니다.

이용자의 지갑과 원장을 보는 화면은 v8.0의 것(10장)이 따로 있고, 거기에는 그 화면의 권한과 감사 기록이 적용됩니다. v10.0은 그것을 넓히지 않았습니다.

### 13.4 한계

- 브라우저로 열어 보지 못했습니다 (HTML 을 문자열로 검사).
- 요약 요청의 부하를 재 보지 않았습니다. 접속자 수 × (60 ÷ 갱신 간격)번의 요청이 1분에 오고, 요청마다 전국 도시의 위험도·랭킹을 읽습니다. 캐시가 없습니다. 이용자가 늘면 전국 부분(모든 이용자에게 같은 값)을 몇 초 동안 캐시하는 것이 첫 번째 대책입니다.
- 도시별·이용자 집단별로 다른 기본값을 줄 수 없습니다 (전체에 하나).
- 알림의 문구는 코드에 있습니다. 관리자가 고칠 수 없습니다.
- v9.0의 일반 설정 경로(`/admin/growth/settings/{키}`)로도 `dashboard` 키를 저장할 수 있습니다. 같은 저장 함수를 거치므로 권한·범위·사유·이력은 똑같이 적용됩니다.
