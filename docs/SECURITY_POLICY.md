# SECURITY_POLICY — 보안 정책

> 기준 v6.0 + v7.0 현실 혜택 · 2026-11-13 · 상태: 1~12장은 정책 (v8.0 서버가 구현한 범위는 각 시스템 문서). **13장은 v7.0 CITY PASS·장학에 적용한 보안으로, 서버에 구현해 로컬 테스트를 통과함. 운영 전**

## 1. 비밀 정보

| 규칙 | 내용 |
|---|---|
| 기록 금지 | 서버 비밀번호, SSH 키, DB 계정, API 키, 토큰을 문서·소스·저장소·채팅 기록·공지에 적지 않는다 |
| 보관 위치 | 서버는 문서 루트 밖의 `.env` (소유자만 읽기). 개발 PC는 환경변수 또는 저장소에서 제외된 `.env.local` |
| 저장소 | `.gitignore`에 `.env*`, 키 파일, 백업, 덤프를 넣는다. 커밋 전에 비밀 값이 섞이지 않았는지 검사한다 |
| 환경 분리 | 개발·스테이징·운영이 서로 다른 계정과 비밀 값을 쓴다 |
| 최소 권한 | 계정마다 필요한 권한만 준다. 애플리케이션은 DB 관리자 계정을 쓰지 않는다 |
| 접속 방식 | 서버 접속은 키 방식을 권장. 배포 전용 키를 따로 둔다 |
| 노출 시 | 노출된 값은 즉시 교체한다. 지우는 것만으로 끝내지 않는다 |
| 클라이언트 | 게임 빌드에 서버 비밀 값을 넣지 않는다. 빌드에 들어간 값은 누구나 꺼낼 수 있다고 본다 |

## 2. 인증과 세션

| 항목 | 정책 |
|---|---|
| 게스트 비밀키 | 서버가 생성한 긴 무작위 값. 발급 때 한 번만 전달. 서버에는 비밀번호 해시로 저장 |
| 기기 보관 | Windows에서는 사용자 계정으로 암호화(DPAPI)한 파일. 평문 저장 금지 |
| 접속 토큰 | 무작위 값. 서버에는 해시만 저장. 수명 24시간 |
| 전송 | HTTPS만. 인증서 검증을 끄지 않는다 |
| 생성 제한 | IP당 게스트 생성 횟수 제한 (계정 대량 생성 방지) |
| 폐기 | 로그아웃, 제재, 이상 징후 시 토큰 폐기 |
| 기록 | 토큰과 비밀키를 로그에 남기지 않는다 |

## 3. 서버 권한과 부정행위 방지

클라이언트는 조작될 수 있다고 전제합니다.

| 원칙 | 내용 |
|---|---|
| 금액은 서버가 | GC, 경험치, 가격, 이자, 확률, 드롭은 서버가 계산한다. 클라이언트가 보낸 금액은 받지 않는다 |
| 보상 검증 | 처치 수, 소요 시간, 순번, 일일 한도를 확인한다 ([COMBAT_SYSTEM](COMBAT_SYSTEM.md) 10장) |
| 소유 확인 | 장착, 사용, 판매 전에 보유 여부를 서버에서 확인한다 |
| 본인 데이터만 | 요청의 대상이 본인 것인지 항상 확인한다 |
| 한도 | 일일 보상, 거래 횟수, 보유량 한도로 피해 범위를 제한한다 |
| 기록 | 검증에서 거절된 요청을 남겨 관리자가 볼 수 있게 한다 |
| 대응 | 반복되는 조작은 관리자가 확인해 제재한다. 자동 영구 정지는 하지 않는다 (오판 방지) |

싱글 플레이 전투의 판정은 클라이언트에서 일어나므로 완벽히 막을 수는 없습니다. 목표는 조작으로 얻을 수 있는 이득을 한도 안에 묶고, 흔적을 남기는 것입니다.

## 4. 금융 거래 보호

| 항목 | 정책 |
|---|---|
| 원자성 | 잔액 변경, 원장 기록, 대응하는 변화는 하나의 트랜잭션 |
| 동시성 | 변경 전 행 잠금. 잠금 순서 고정 |
| 중복 방지 | 변경 요청마다 중복 방지 키 |
| 음수 금지 | 잔액이 음수가 되는 거래 거절. DB 제약으로도 막음 |
| 원장 | 추가만 가능. 수정·삭제 없음 |
| 점검 | 매일 잔액과 원장 합계 대조 |
| 수동 조정 | 관리자 기능으로만. 사유와 담당자 기록 |
| 현실 화폐 | 결제, 환전, 현금 상환 기능을 만들지 않는다 |

## 5. 웹과 API

| 위협 | 대책 |
|---|---|
| SQL 삽입 | 준비된 문장(바인딩)만 사용. 문자열로 SQL을 이어 붙이지 않는다 |
| 스크립트 삽입 (XSS) | 모든 출력 이스케이프. 콘텐츠 보안 정책 유지 (자기 출처만). 닉네임·채팅·공지 포함 |
| 요청 위조 (CSRF) | 홈페이지 양식과 관리자에 토큰. API는 쿠키가 아닌 Bearer 토큰 |
| 과도한 요청 | 경로별 요청 제한. 인증·금융 경로는 더 엄격히 |
| 정보 노출 | 오류 응답에 내부 정보 없음. PHP 버전 헤더 숨김. 디렉터리 목록 금지 |
| 파일 업로드 | 플레이어 업로드 기능 없음. 관리자 업로드는 형식·크기 검사, 실행 불가 경로에 저장 |
| 파일 접근 | 코드, 설정, 백업, 로그는 문서 루트 밖 |
| 전송 | HTTPS 강제, HSTS 유지 |
| 의존성 | 외부 라이브러리는 최소한으로. 버전을 고정하고 보안 공지를 확인 |
| 입력 검증 | 형식, 길이, 범위, 허용 값 검사 |

운영 사이트에 이미 적용된 보안 헤더를 약화시키지 않습니다.

## 6. 관리자

[ADMIN_SYSTEM](ADMIN_SYSTEM.md) 2장의 내용을 따릅니다. 요약: 별도 계정, 강한 비밀번호 해시, 2단계 인증 필수, 세션 쿠키 보호, CSRF 토큰, 로그인 시도 제한, 접속 IP 제한(선택), 역할별 권한, 모든 변경의 감사 기록.

관리자 계정을 여러 사람이 함께 쓰지 않습니다.

## 7. 미성년자 보호

초등학생이 이용한다는 것을 전제로 합니다.

| 영역 | 정책 |
|---|---|
| 나이를 모를 때 | 미성년자로 보고 가장 제한된 설정을 적용 |
| 결제 | 현실 결제 기능 없음 |
| 대출 | 1건 제한, 낮은 한도, 이자 상한, 복리 없음, 연체 가산 없음, 장기 연체 정리, 압박 알림 없음 ([LOAN_CREDIT_SYSTEM](LOAN_CREDIT_SYSTEM.md) 2장) |
| 투자 | 변동 한도, 최저 가격, 거래 횟수 한도, 빚내서 투자 불가, 권유 알림 없음 ([STOCK_SYSTEM](STOCK_SYSTEM.md) 7장) |
| 채팅 | 제한형부터. 욕설·개인정보 필터, 신고·차단, 1:1 비공개 대화 없음 ([COMMUNITY_SYSTEM](COMMUNITY_SYSTEM.md) 5장) |
| 개인정보 | **게임은** 실제 주소, 위치, 학교, 연락처를 수집하지 않음. 닉네임에 실명을 쓰지 않도록 안내. 예외는 장학 신청 하나뿐이고(홈페이지에서, 본인과 보호자의 동의를 받아, 암호화해 저장) 게임 화면으로는 받지 않음 (13장) |
| 표현 | 피·잔혹 표현 없음. 적은 기계 |
| NPC | 플레이어로 위장하지 않음 |
| 이용 시간 | 늦은 밤 접속을 유도하는 한정 이벤트를 만들지 않음. 긴 플레이 뒤 쉬어 가라는 안내 (보리의 한마디) |
| 설계 | 불안을 자극하는 문구, 놓치면 손해라는 압박, 확률에 돈을 거는 구조를 쓰지 않음 |
| 보호자 | 홈페이지에 보호자 안내 제공 |

## 8. 개인정보

| 항목 | 정책 |
|---|---|
| 수집 최소화 | 게스트는 개인정보를 받지 않는다. 서버가 붙인 ID와 게임 데이터만 가진다. CITY PASS 도 개인정보를 받지 않는다. 장학 신청만 이름·태어난 해·학교급·연락처를 받는다 ([PRIVACY_DATA_FLOW](PRIVACY_DATA_FLOW.md)) |
| 접속 기록 | IP 등은 보안과 부정행위 대응에 필요한 범위와 기간만 보관 |
| 계정 연결 | 개인정보가 필요한 수단은 법적 검토 뒤 도입. 그 전에는 개인정보가 필요 없는 이어하기 코드 방식 |
| 닉네임 | 공개되는 정보임을 안내. 실명·연락처 형태는 거부 |
| 채팅 | 보관 기간이 지나면 자동 삭제 |
| 삭제 요청 | 계정과 데이터 삭제 요청을 처리하는 절차를 둔다. 금융 원장은 플레이어와의 연결을 끊은 뒤 통계용으로만 남긴다 |
| 관리자 열람 | 필요한 역할만, 열람 기록을 남김 |
| 개발 환경 | 운영 데이터를 개발 PC로 가져오지 않는다 |
| 문서 | 개인정보처리방침을 실제 수집 내용과 일치하게 유지 |

## 11. 사고 대응

| 단계 | 내용 |
|---|---|
| 발견 | 감시 지표, 관리자 로그, 이용자 신고 |
| 차단 | 점검 모드, 문제 기능 끄기, 관련 토큰 폐기, 노출된 비밀 값 교체 |
| 파악 | 원장과 로그로 범위 확인. 증거 보존 |
| 복구 | 정정 거래(원장에 반대 행)로 바로잡기. 덤프 복원은 마지막 수단 |
| 알림 | 영향받은 이용자와 필요한 기관에 알림 (요건은 법적 검토) |
| 재발 방지 | 원인과 조치를 기록하고 테스트를 추가 |

기능을 설정으로 끌 수 있게 만듭니다 (은행, 주식, 대출, 채팅 각각). v7.0의 현실 혜택 기능 넷은 관리자 화면에서 하나씩 끌 수 있고, 서버 설정 `BENEFITS_LOCKED=1`로 한꺼번에 잠글 수 있습니다.

## 12. 개발 규칙

- 운영 서버에서 직접 코드를 고치지 않습니다. 모든 변경은 저장소 → 스테이징 → 운영 순서로 갑니다.
- 운영 DB를 손으로 고치지 않습니다.
- 기존 서비스에 영향을 주는 변경은 사전 승인을 받습니다 ([SERVER_DEPLOYMENT](SERVER_DEPLOYMENT.md) 7장).
- 다른 프로젝트의 계정이나 인증정보를 이 프로젝트에 빌려 쓰지 않습니다.
- 다른 게임의 캐릭터, 에셋, 데이터를 복제하지 않습니다.
- 금융과 인증 코드는 테스트 없이 배포하지 않습니다 ([TEST_PLAN](TEST_PLAN.md) 4장).

## 13. 현실 혜택: CITY PASS 와 장학 (v7.0)

게임 밖의 가치(쿠폰, 장학 지원)와 실제 개인정보를 다루므로 게임 기능보다 엄격하게 다룹니다. 설명은 [REAL_WORLD_REWARDS_POLICY](REAL_WORLD_REWARDS_POLICY.md), [PRIVACY_DATA_FLOW](PRIVACY_DATA_FLOW.md), [COUPON_SYSTEM](COUPON_SYSTEM.md), [ADMIN_SYSTEM](ADMIN_SYSTEM.md) 11장.

### 13.1 게임 경제와의 분리

| 원칙 | 구현 |
|---|---|
| GC·전투 성적·랭킹·아이템·플레이 시간·결제액이 현실 혜택의 기준이 되지 않는다 | 혜택 서비스 코드는 지갑·원장·캐릭터·전투·도시 테이블을 읽지 않는다. 테스트가 소스를 훑어 확인한다 |
| 교환 기능이 없다 | GC ↔ 쿠폰·상품·현금, 쿠폰 구매, 장학금의 게임 내 지급에 해당하는 API·화면·스위치가 없다. 주소를 짐작해 불러도 없다 (테스트) |
| 혜택이 게임에 영향을 주지 않는다 | 쿠폰을 받거나 쓰고, 장학을 신청해도 GC·경험치·아이템이 바뀌지 않는다 (테스트가 전후의 지갑과 원장을 비교) |

### 13.2 기본은 꺼짐

- 기능 넷은 꺼진 채로 설치된다. 법률 검토 완료의 기록(문서 번호, 검토한 곳, 날짜)과 **다른 최고 관리자**의 승인이 있어야 켜진다.
- DB 의 스위치만 고쳐서는 켜지지 않는다 (검토 기록을 함께 확인).
- 검토 상태가 바뀌면 자동으로 꺼진다. 준법 담당이 언제든 끌 수 있다. `BENEFITS_LOCKED=1`은 모든 것에 우선한다.

### 13.3 쿠폰

| 위협 | 대책 |
|---|---|
| 같은 쿠폰을 두 번 씀 | 조건부 `UPDATE`(상태가 `issued`이고 코드가 살아 있을 때만) + `coupon_redemptions.coupon_id` 유일 색인. 한 트랜잭션 안에서 처리하고 거래 로그(`coupon_events`)에 남김 |
| 같은 요청이 두 번 와서 쿠폰이 두 장 생김 | 발급에 중복 방지 키 필수. 회원 행을 잠근 채 한도 확인 |
| QR·코드의 유출 | 코드는 5분, 한 번. 새로 만들면 앞의 것은 죽음. 서버에는 해시만. QR 에 개인정보·회원번호·쿠폰 번호 없음 |
| 코드 추측 | 31자 가운데 10자의 무작위 값. 상점 계정마다 틀린 코드 10번/10분이면 차단, 기록 |
| 이용자가 스스로 사용 처리 | 사용 처리는 상점 계정으로 로그인한 화면에서만. 이용자 API 에는 그 기능이 없음 |
| QR 주소를 여는 것만으로 사용 처리 | GET 은 코드를 칸에 채울 뿐. 사용 처리는 직원이 확인한 뒤의 POST (CSRF 토큰) |
| 상점이 남의 쿠폰·데이터를 봄 | 모든 조회와 처리에 업체(지점) 조건. 다른 업체의 코드는 "없는 코드"로 답함 |
| 상점 계정 탈취 | 임시 비밀번호는 첫 로그인에 강제 변경, 12자 이상, 5번 틀리면 15분 잠금, IP당 시도 제한, 30분 무조작·12시간 만료, `SameSite=Strict` 쿠키, 운영팀이 비활성화·초기화. **2단계 인증은 없음** (한계) |
| 제휴하지 않은 상점이 표시됨 | 계약 번호·기간·청소년 적합 확인·지점이 있고 **다른 관리자가 승인한** 업체만 표시. 계약이 끝나면 자동으로 사라짐 |
| 부정 사용 | 최근 24시간의 신호를 관리자 화면에 표시 (확인 실패, 몰린 사용 처리, 잦은 코드 생성). 자동 차단은 없음 |

### 13.4 장학 신청의 개인정보

| 원칙 | 구현 |
|---|---|
| 고위험 정보를 받지 않는다 | 주민등록번호, 계좌번호, 주소, 생년월일의 월·일, 파일을 받는 칸과 열이 없다 |
| 목적별 분리 | 심사용(신청서), 본인·연락용, 동의용을 다른 테이블에. 심사위원 화면은 본인·연락 테이블을 읽지 않는다 |
| 암호화 | 이름, 학교, 이메일, 전화, 신청서, 제출 자료, 보호자 이름·연락처, 이의신청 사유를 AES-256-GCM 으로. 키는 서버 `.env`의 `DATA_KEY`에만. 키가 없으면 접수를 켤 수 없고 평문 저장 경로가 없다 |
| 접근 제한 | 업무별 역할. 개인정보는 장학 담당만, 사유를 적고, **열기 전에 기록** |
| 보관 기한 | 기한이 지나면 예약 작업이 개인정보를 비운다 (선정되지 않음 180일, 선정 5년, 철회 30일 — 기본값, 검토 필요) |
| 미성년자 | 보호자의 일회용 주소 동의 + 담당자의 확인 두 단계를 거쳐야 심사로 넘어간다 |
| 게임으로 가지 않는다 | 게임 API 는 신청의 상태만 돌려준다. 신청서와 개인정보는 응답에 없다 |
| 자동 송금 없음 | 지급은 상태 기록뿐. 계좌 정보를 저장하지 않는다 |

### 13.5 업무 분리

- 역할 다섯(CITY PASS 담당, 장학 담당, 심사위원, 준법·개인정보 담당, 지급 담당)을 더했다. 게임 운영 역할은 혜택 화면을 볼 수 없다.
- 만든 사람과 승인하는 사람이 달라야 하는 일이 일곱 가지 있다 ([ADMIN_SYSTEM](ADMIN_SYSTEM.md) 11.4).
- 평가 점수는 심사위원만 넣는다 (최고 관리자도 못 한다).

### 13.6 홈페이지와 상점 화면

- 자바스크립트와 외부 자원이 없다. `Content-Security-Policy: default-src 'none'; style-src 'self'; img-src 'self'; …`
- 값을 바꾸는 요청은 POST 만, 출처(`Origin`) 확인과 CSRF 토큰. 모든 출력 이스케이프. SQL 은 준비된 문장만.
- 홈페이지 로그인은 게임 안에서 받은 일회용 코드(5분, 한 번, 해시 저장)로 한다. 비밀번호를 새로 만들지 않는다.
- 로그인한 화면은 저장·색인 금지.

### 13.7 한계 (운영 전에 보완하거나 받아들일지 정할 것)

1. 상점 계정에 2단계 인증이 없다.
2. 보호자 본인임을 기술로 증명하지 못한다 (본인확인 서비스 연동 없음). 담당자의 확인 단계에 기댄다.
3. 암호화 키의 교체(회전) 도구가 없다. 키와 DB 백업의 분리 보관은 운영 절차로 지켜야 한다.
4. DB 계정 수준의 권한 분리를 하지 않았다 (애플리케이션 계정 하나).
5. `Origin` 헤더가 없는 POST 는 출처 확인을 통과한다. 로그인 뒤의 요청은 CSRF 토큰이 막지만 로그인 요청은 그렇지 않다.
6. 쿠폰의 동시 사용 처리를 실제 병렬 부하로 시험하지 않았다 (조건부 갱신과 유일 색인의 동작만 확인).
7. 실제 브라우저·웹 서버(Apache / nginx)·HTTPS 위에서 돌려 보지 않았다. 외부 보안 점검을 받지 않았다.
8. 한 사람이 관리자 계정을 둘 갖는 것은 기술로 막을 수 없다.
9. 부정 사용 탐지에 알림과 자동 차단이 없다.
