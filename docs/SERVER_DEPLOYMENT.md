## 3. 지시서와 실제의 차이 — PHP 버전

지시서는 PHP 8.3 이상을 요구하지만 운영 사이트는 PHP 7.3.33으로 동작하고 있습니다. PHP 7.3은 2021년 12월에 보안 지원이 끝난 버전입니다.

| 방안 | 내용 | 평가 |
|---|---|---|
| A | 서버에 PHP 8.3을 추가하고 이 사이트만 8.3으로 전환 | **권장.** 다른 사이트에 영향 없음. 기존 v1 코드가 8.3에서 도는지 스테이징에서 먼저 확인 필요 |
| B | PHP 7.3을 유지하고 7.3 호환 코드로 작성 | 비권장. 지원이 끝난 버전이고 지시서와 다름 |
| C | 서버 전체의 PHP를 8.3으로 교체 | 비권장. 같은 서버의 다른 사이트가 깨질 수 있음 |

방안 A도 서버 설정을 바꾸는 작업이므로 승인이 필요합니다. 서버에 이미 PHP 8.3이 설치되어 있고 사이트별로 고를 수 있는 구성이라면 작업이 작아집니다 (2장 2번에서 확인).

응답 헤더에 PHP 버전이 드러나는 것(`X-Powered-By`)은 끄는 것을 권합니다. 이것도 설정 변경이므로 함께 승인받습니다.

## 5. 서버 디렉터리 구조 (목표)

실제 구조는 2장의 조사 뒤 확정합니다. 원칙은 다음과 같습니다.

```
<사이트 경로>/
  public/          문서 루트. index.php와 정적 파일만
  src/             애플리케이션 코드
  config/          설정 (비밀 값 없음)
  migrations/      DB 마이그레이션
  storage/         로그, 캐시, 업로드 (웹에서 직접 접근 불가)
  .env             비밀 값. 소유자만 읽기
<사이트 경로 밖>/
  backups/         DB 덤프, 배포 전 백업
  builds/          게임 빌드 파일 (다운로드는 애플리케이션을 거쳐 제공)
```

- 코드, 설정, `.env`, 백업은 문서 루트 **밖**에 둡니다.
- 문서 루트를 바꿀 수 없는 구성이면 웹 서버 설정으로 `public` 외 경로의 접근을 막습니다.
- 기존 사이트가 다른 구조라면, 구조 변경은 별도 단계로 승인받아 진행합니다.

## 6. 배포 절차

### 6.1 배포 전

1. 자동 테스트 통과.
2. 스테이징에 같은 버전을 배포해 확인. 마이그레이션은 스테이징에서 먼저 실행.
3. 배포 내용과 영향 범위를 정리해 승인 요청.

### 6.2 백업

배포 때마다, 변경 전에 수행합니다.

| 대상 | 방법 |
|---|---|
| DB | `city_guardians`만 덤프 (일관된 시점으로). 다른 DB는 건드리지 않음 |
| 파일 | 사이트 경로를 묶어 보관 (`.env` 포함, 백업 폴더는 소유자만 접근) |
| 보관 | 문서 루트 밖. 날짜와 버전으로 이름. 최근 배포 5회분과 일일 백업 14일분 유지 |
| 확인 | 파일 크기와 덤프 끝부분을 확인해 백업이 온전한지 본 뒤 진행 |

**첫 작업 전에 현재 상태 전체를 한 번 백업하고**, 그 백업은 지우지 않고 보관합니다.

### 6.3 배포

1. 새 버전을 새 폴더에 올립니다 (기존 파일 위에 바로 덮어쓰지 않음).
2. 마이그레이션을 실행합니다. 추가만 하는 변경이어야 합니다 ([DATABASE](DATABASE.md) 5장).
3. 새 버전으로 전환합니다.
4. 확인: `/api/v1/health`, 홈페이지 주요 경로, 게스트 생성부터 구매까지의 점검 스크립트.
5. 문제가 있으면 바로 이전 버전으로 되돌립니다.

전환 방식(폴더 교체, 링크 전환 등)은 서버 구성을 확인한 뒤 정합니다.

### 6.4 되돌리기

| 상황 | 방법 |
|---|---|
| 코드 문제 | 이전 버전 폴더로 전환. 마이그레이션이 추가만 했으므로 이전 코드가 그대로 동작 |
| 데이터 문제 | 원인 파악 후 정정 마이그레이션. 덤프 복원은 마지막 수단이며 복원 시점 이후의 플레이 기록이 사라지므로 별도 승인 |

### 6.5 배포 수단

SSH를 통한 파일 전송과 원격 명령. 배포 스크립트는 `tools/deploy/`에 두고 접속 정보는 환경변수에서 읽습니다. 스크립트는 대상 경로가 이 사이트의 경로인지 확인한 뒤에만 동작하게 합니다.

## 11. v8.0 게임 서버 (`server/`)

### 11.1 구성

```

  bin/             migrate.php, tick.php, create-admin.php, gen-seed.php, new-data-key.php (명령줄 전용)
  tests/           테스트 (운영 서버에 올리지 않음)
```

| 항목 | 내용 |
|---|---|

### 11.2 올리기 전에 확인할 것

**운영 서버에는 이미 `/api/v1`(v1.0.0)과 그 DB가 있습니다.** 이 서버를 같은 경로와 같은 DB에 그대로 올리면 기존 API를 바꿔치기하게 됩니다. 아래를 확인하고 승인받기 전에는 올리지 않습니다.

| # | 확인할 것 | 이유 |
|---|---|---|
| 1 | 기존 `/api/v1`의 소스와 경로 목록 | v8.0 서버에는 기존 API의 기능(가방, 상점, 은행 등)이 없음. 덮어쓰면 그 기능이 사라짐 |
| 2 | 운영 DB의 테이블 구조 | `players`, `wallets`, `regions` 등이 다른 구조로 이미 있으면 사전 점검에서 멈춤 ([DATABASE](DATABASE.md) 0장). 멈추지 않더라도 기존 코드와 같은 테이블을 함께 쓰게 되므로 대조가 필요 |
| 3 | 지역 코드 | 운영 DB는 229곳, 이 저장소는 230곳. `0004`는 지역 목록이 비어 있을 때만 넣으므로 운영 DB에서는 아무것도 넣지 않음. **그 경우 기존 코드가 클라이언트의 지역 코드와 같은지 확인해야 함** |
| 4 | 기존 `/admin`이나 같은 이름의 경로 | 지금은 404지만 다른 경로에 관리자가 있을 수 있음 |
| 5 | 기존 예약 작업 | `bin/tick.php`와 겹치는 작업이 있는지 |

기존 API를 살려 둔 채 시험하는 방법: **별도의 설치 경로**(예: 스테이징 하위 도메인, 또는 `/cg8` 같은 별칭)와 **별도의 DB**(`city_guardians_staging`)에 먼저 올립니다. 서버 코드는 설치 경로가 어디든 동작합니다 (경로와 쿠키의 범위를 스스로 맞춤).

### 11.3 올리는 순서 (승인 뒤)

1. 6.2의 백업.
2. `server/`의 `public`, `src`, `migrations`, `bin`, `.htaccess`를 새 폴더에 올립니다. `tests`와 `storage`는 올리지 않습니다.
3. 웹 서버의 문서 루트(또는 별칭)가 `public/`만 가리키게 합니다.
4. `.env`를 서버에서 만듭니다 (`.env.example`을 복사해 값을 채움. 소유자만 읽기). `APP_ENV`, `DB_*`, `ADMIN_COOKIE_SECURE=1`, 필요하면 `ADMIN_ALLOW_IPS`.
5. `php bin/migrate.php` — 상태와 사전 점검 결과를 봅니다. 아무것도 바꾸지 않습니다.
6. `php bin/migrate.php --apply --i-have-approval-and-backup` — 적용. 스테이징에서 먼저.
7. `php bin/create-admin.php <아이디> super` — 첫 관리자. TOTP 비밀값을 일회용 코드 앱에 등록.
8. 확인: `GET /api/v1/health`, 게스트 생성 → 세 모드 한 번씩 → `GET /api/v1/cities/risk`, `/admin` 로그인, `.env`·`src/`·`migrations/`가 웹에서 열리지 않는지.
9. 예약 작업 등록 (11.4).

애플리케이션의 DB 계정에는 이 DB의 `SELECT`, `INSERT`, `UPDATE`, `DELETE`만 줍니다. 마이그레이션을 적용할 때만 `CREATE`가 있는 계정을 씁니다 ([DATABASE](DATABASE.md) 6장). 지금의 `bin/migrate.php`는 `.env`의 계정 하나로 접속하므로, 적용할 때는 환경변수(`DB_USER`, `DB_PASS`)로 마이그레이션 계정을 넘깁니다.

## 12. v7.0 현실 혜택 (CITY PASS · SCHOLARSHIP)

| 키 | 내용 |
|---|---|
| `BENEFITS_LOCKED` | 보통 `0`. `1`이면 네 기능을 모두 끔 |
| `DATA_KEY` | 장학 신청서의 개인정보를 암호화하는 키. `php bin/new-data-key.php`로 만듦. 비어 있으면 장학 신청 기능을 켤 수 없음 |
| `PUBLIC_BASE_URL` | 홈페이지의 바깥 주소 (`https://…`). 쿠폰 QR, 로그인·신청·보호자 확인 주소를 만들 때 씀. 비어 있으면 QR 에 주소 없이 코드만 들어감 |
| `WEB_COOKIE_SECURE` | 운영에서는 `1` |
| `WEB_LOGIN_PER_10MIN`, `MERCHANT_LOGIN_PER_10MIN` | 한 주소에서 할 수 있는 로그인 시도 수 |
| `PARTNER_CONTACT_EMAIL` | 제휴 문의를 받는 주소. 비어 있으면 제휴 문의 페이지에 "준비 중" |

**`DATA_KEY`의 관리:**

- 키를 저장소, 문서, 채팅, 이슈에 적지 않습니다. 서버의 `.env`(소유자만 읽기)에만 둡니다.
- **DB 백업과 다른 곳에** 따로 보관합니다. 백업과 키가 함께 새면 암호화가 소용없고, 키를 잃으면 저장된 신청서를 읽을 수 없습니다.
- 신청서가 저장된 뒤에는 키를 바꾸지 않습니다. 키를 바꾸며 다시 암호화하는 도구는 아직 없습니다 ([PRIVACY_DATA_FLOW](PRIVACY_DATA_FLOW.md) 4장, 9장).
- 스테이징과 운영은 서로 다른 키를 씁니다. 운영 DB 를 스테이징으로 복사하지 않습니다 (신청자의 개인정보가 들어 있음).

### 12.5 올린 뒤의 순서 (승인 뒤)

11.3의 1~9를 마친 다음:

1. `.env`에 12.3의 값을 넣습니다 (`DATA_KEY`는 서버에서 만들어 바로 넣음).
2. 확인: `/city-pass`, `/scholarship`이 "준비 중"으로 열리는지, `/login`이 열리는지, `/merchant`가 로그인으로 넘어가는지, 토큰 없는 `GET /api/v1/city-pass/profile`이 401 인지, 게스트로 `POST /api/v1/city-pass/membership`이 `403 FEATURE_DISABLED`인지.
3. 업무별 관리자 계정을 만듭니다: `php bin/create-admin.php <아이디> <역할>` — `compliance`, `pass_manager`, `sch_manager`, `reviewer`, `finance` ([ADMIN_SYSTEM](ADMIN_SYSTEM.md) 11.1). 한 사람에게 여러 역할의 계정을 주면 "만든 사람과 승인하는 사람이 달라야 한다"는 장치가 뜻을 잃습니다.
4. **여기까지가 배포입니다.** 그 다음은 운영 절차이고 각각 사전 승인이 필요합니다: 법률 검토 기록 → 기능 켜기 → 제휴 상점·혜택 등록과 승인 → 상점 계정 발급 (임시 비밀번호는 관리자 화면에 한 번만 보이고, 상점이 첫 로그인 때 바꿈) → 장학 프로그램 등록과 공고.

**실사용자에게 쿠폰을 내거나 장학 신청을 받는 것은 배포 승인과 별개의 승인이 필요합니다.**

새 작업을 등록하지 않습니다. 11.4의 `php bin/tick.php`가 다음을 함께 합니다.

| 일 | 내용 |
|---|---|
| 쿠폰 만료 | 유효기간이 지난 쿠폰을 "만료"로 적음 (사용 처리 때에도 기간을 따로 확인하므로, 작업이 멈춰 있어도 지난 쿠폰은 쓸 수 없음) |
| 개인정보 삭제 | 보관 기간이 끝난 장학 신청의 신청서, 신청자 정보, 제출 자료, 보호자 정보, 평가 의견을 지움 ([PRIVACY_DATA_FLOW](PRIVACY_DATA_FLOW.md) 5장) |
| 접속 정리 | 끝난 홈페이지·상점 접속 기록 |

- 기능이 꺼져 있어도 돕니다 (꺼진 뒤에도 보관 기간은 흐름).
- **이 작업이 돌지 않으면 개인정보가 보관 기간을 넘겨 남습니다.** 장학 신청을 받기 시작한 뒤에는 예약 작업이 도는지를 10장의 점검에 넣습니다. v8.0의 침공 판정과 달리 요청이 올 때 대신 처리되지 않습니다.
- 삭제는 되돌릴 수 없습니다. 보관 기간의 기본값(선발되지 않은 신청 180일, 선발된 신청 5년, 프로그램을 보관 처리한 뒤 30일)은 법률 검토로 확정해야 합니다.

### 12.7 백업과 개인정보

- DB 백업에는 암호화된 신청서와, 암호화되지 않은 신청 상태·평가 점수·감사 로그가 들어 있습니다. 백업 파일의 접근 권한과 보관 기간을 정합니다.
- 예약 작업이 지운 개인정보도 **그 전에 만든 백업에는 남아 있습니다.** 백업의 보관 기간이 개인정보의 보관 기간보다 길지 않게 합니다.
- 웹 서버의 접속 로그에는 주소가 남습니다. 보호자 확인 주소(`/scholarship/consent/{토큰}`)와 상점 화면의 `?code=`가 접속 로그에 남으므로, 접속 로그의 접근 권한과 보관 기간도 함께 정합니다. 쿠폰의 일회용 코드는 5분 뒤에는 쓸 수 없고 DB 에는 해시로만 저장되지만 ([COUPON_SYSTEM](COUPON_SYSTEM.md) 4장), 보호자 확인 주소는 동의할 때까지 살아 있으므로 접속 로그를 볼 수 있는 사람을 좁혀야 합니다.

## 13. v9.0 도시 성장, 협동 방어전, 지방세

v9.0에서 `server/`에 도시 성장·지방세·참여예산·협동 방어전의 대기실을 더했고, 협동 방어전의 전투를 맡는 **실시간 서버**(`realtime/`)를 새로 만들었습니다. **운영 서버에는 올리지 않았고 접속하지도 않았습니다.** 11장과 12장의 내용이 그대로 적용되고, 이 장은 더 필요한 것만 적습니다.

### 13.1 올려도 켜지지 않는다

코드를 올리고 마이그레이션을 적용해도 플레이어에게 달라지는 것은 "도시 살림" 화면에서 수를 볼 수 있다는 것뿐입니다.

| 기능 | 처음 상태 | 켜는 곳 |
|---|---|---|
| 지방세 3종 (거래세, 사업세, 재산세) | 꺼짐. 한 푼도 걷지 않음 | 관리자 → 지방세 정책 |
| 참여예산 | 꺼짐 (`budget.enabled = 0`) | 관리자 → 참여예산 관리 |
| 협동 방어전 (온라인) | 꺼짐 (`coop.enabled = 0`). 켜도 `REALTIME_SECRET`과 `REALTIME_URL`이 없으면 열리지 않음 | 관리자 → 협동 디펜스 모니터링 + 서버 설정 |
| 지역 콘텐츠 배포 | `CONTENT_BASE_URL`이 없으면 배포 단추가 동작하지 않음 | 서버 설정 + 관리자 → 도시 콘텐츠 배포 관리 |
| 전입자 집계 | 동작함. 기본 규칙(`linked`)은 **연결된 계정만** 세므로, 계정 연결 기능이 없는 지금은 모든 도시가 0명 | 관리자 → 도시 성장 관리 |
| 이사 | 동작함 (수수료와 기다리는 기간이 있음). 끌 수 있음 | 관리자 → 도시 성장 관리 |

세금이 꺼져 있는 동안의 구매·보상 금액은 v8.0과 같습니다 (`TaxTest::testEveryTaxIsOffByDefaultAndNothingChangesFromV8`).

### 13.2 DB

마이그레이션 `0008`~`0011`은 새 테이블 21개와 초기값만 더합니다. 기존 테이블의 구조를 바꾸지 않습니다. 적용 순서와 되돌리는 방법은 [DATABASE](DATABASE.md) 9장.

**격리 수준:** v9.0부터 이 애플리케이션의 DB 접속은 `READ COMMITTED`를 씁니다 (`SET SESSION …`, 서버의 설정은 건드리지 않음). 잠금을 잡은 뒤 다시 읽은 값이 최신이어야 동시 요청에서 금액이 사라지지 않기 때문입니다 (`ConcurrencyTest`). **v8.0·v7.0의 기능에도 같이 적용됩니다.** 올리기 전에 확인할 것:

| 확인 (2장의 조사 항목 13) | 방법 | 이유 |
|---|---|---|
| `binlog_format`이 `STATEMENT`가 아님 | `SELECT @@global.log_bin, @@global.binlog_format` | 바이너리 로그를 `STATEMENT`로 쓰는 서버에서는 `READ COMMITTED`의 쓰기가 오류가 됨. MySQL 8 의 기본값은 `ROW`. `log_bin`이 꺼져 있으면 상관없음 |
| 같은 DB 를 쓰는 기존 코드 | 11.2의 대조 | 격리 수준은 접속마다 정하므로 기존 코드의 접속에는 영향이 없음. 다만 같은 테이블을 함께 쓴다면 대조가 필요 |

`STATEMENT`인 서버라면 올리지 않고 먼저 상의합니다 (서버의 설정을 바꾸는 것은 7장의 "하지 않는 일"에 가깝고, 다른 사이트에 영향이 있습니다).

### 13.3 설정 (`.env`)

`.env.example`에 본보기가 있습니다. 값은 서버의 `.env`나 환경변수에만 둡니다.

| 이름 | 내용 |
|---|---|
| `REALTIME_SECRET` | 게임 서버와 실시간 서버가 나눠 갖는 서명 키. 32자 이상의 무작위 값. 입장권과 내부 요청에 서명. **두 서버의 환경에만 두고 저장소·문서·채팅에 적지 않음.** 비어 있으면 협동 방어전이 열리지 않음 |
| `REALTIME_URL` | 플레이어에게 알려 줄 주소 (`wss://…/ws`). `ws://`는 `127.0.0.1`과 `localhost`만 받음 |
| `CONTENT_BASE_URL` | 지역 콘텐츠를 올려 둔 주소의 앞부분 (`https://`만). 비어 있으면 배포할 수 없고 클라이언트는 내장된 기본 거리만 씀 |

서명 키를 바꾸려면 두 서버의 값을 함께 바꾸고 실시간 서버를 다시 띄웁니다. 그 순간 진행 중인 판은 끊깁니다 (13.4의 재시작과 같음).

### 13.4 실시간 서버

| 항목 | 내용 |
|---|---|
| 무엇 | `realtime/src` (ASP.NET Core, 외부 패키지 없음). 협동 방어전의 전투 상태와 전술 핑을 WebSocket 으로 동기화. 전투 규칙은 클라이언트와 같은 C# 소스(`client/Assets/CityGuardians/Domain`)를 그대로 컴파일 |
| 필요한 것 | **.NET 8 의 ASP.NET Core 런타임.** 지금 운영 서버에 있는지 모름 (2장의 조사 항목 12). 설치는 승인 항목 |
| 만들기 | 저장소 전체가 있는 곳에서 `dotnet publish realtime/src -c Release -o <출력>` (클라이언트의 `Domain` 폴더를 함께 컴파일하므로 `realtime/`만 떼어서는 빌드되지 않음). 출력 폴더만 서버로 옮김 |
| 띄우기 | `dotnet CG.Realtime.dll`. 설정이 틀리면 이유를 적고 종료 코드 2 로 끝남 (비밀값은 찍지 않음) |
| 관리 | 죽으면 다시 뜨게 (systemd 등). **정상 종료 신호(SIGTERM)** 로 내려야 진행 중인 판의 결과가 보고됨 |
| 대수 | **한 대만.** 방이 메모리에만 있음. 두 대를 띄우면 같은 판의 사람들이 서로 다른 방에 들어감 |
| 접속 | `127.0.0.1:8090`에서만 듣고, 앞단의 웹 서버가 `wss://<도메인>/ws`를 그리로 중계 (TLS 는 웹 서버가 끝냄). 밖으로 새 포트를 열지 않음. 중계의 유휴 시간 제한은 30초보다 길게 (클라이언트가 15초마다 신호를 보냄) |
| 시계 | 내부 요청의 서명은 시각이 **60초** 넘게 어긋나면 거절됨. 두 서버의 시계를 맞춤 (NTP). 같은 서버에 두면 문제없음 |
| 상태 확인 | `GET http://127.0.0.1:8090/health` → 방과 연결의 수 |
| 로그 | 표준 출력 (방 열림·시작·종료, 결과 반영, 거절된 접속). 계정의 공개 ID 와 판 ID 만 나오고 입장권·서명·주소 뒤의 값은 나오지 않음 |

실시간 서버의 환경변수:

| 이름 | 기본값 | 내용 |
|---|---|---|
| `REALTIME_SECRET` | (필수) | 게임 서버와 같은 값 |
| `GAME_API_URL` | (필수) | 게임 서버 API 의 주소. 예: `https://<도메인>/api/v1`. `http://`는 `127.0.0.1`만 |
| `REALTIME_LISTEN` | `http://127.0.0.1:8090` | 듣는 주소 |
| `REALTIME_ALLOWED_ORIGINS` | (없음) | 브라우저에서 올 때 허용할 Origin (쉼표로 구분). Origin 이 없는 접속(앱)은 그대로 받음 |
| `REALTIME_TRUST_PROXY` | `0` | 앞단 프록시의 `X-Forwarded-For`를 믿을지. **프록시 뒤에 있을 때만 1** (아니면 주소당 접속 제한을 속일 수 있음) |
| `REALTIME_CLOSE_ORPHANS` | `1` | 재시작 뒤 게임 서버에 "전투 중"으로 남은 판을 보상 없이 닫을지. 한 대만 돌릴 때의 값 |
| `REALTIME_MAX_CONNECTIONS` / `_PER_IP` / `REALTIME_MAX_ROOMS` | 2000 / 20 / 300 | 한도 |

게임 서버의 `/api/v1/internal/…` 세 경로는 실시간 서버만 부릅니다. 서명이 맞지 않으면 없는 주소처럼 404 로 답하므로 열려 있어도 쓸 수 없지만, 두 서버가 같은 곳에 있다면 웹 서버에서 이 경로를 `127.0.0.1`로만 받게 하면 한 겹이 더 생깁니다.

**재시작의 영향:** 실시간 서버를 다시 띄우면 그때 진행 중이던 판은 이어 갈 수 없습니다. 정상 종료면 그 시점의 결과가 패배로 보고되고, 갑자기 죽었으면 다시 뜬 뒤 `abandoned`로 닫힙니다 (보상 없음, 하루 횟수도 세지 않음). 점검 시간에 내리거나, 먼저 관리자 화면에서 협동 방어전을 꺼 새 판을 막은 뒤 진행 중인 판이 끝나기를 기다립니다. 게임 서버(PHP)만 올릴 때는 실시간 서버를 건드리지 않아도 됩니다 — 단, 전투 규칙(`Domain`)이나 두 서버 사이의 형식이 바뀐 판은 함께 올립니다.

### 13.5 올리는 순서 (승인 뒤)

1. 11.2와 13.2의 확인 (기존 API·DB 와의 대조, `binlog_format`).
2. 스테이징 경로와 스테이징 DB 에 먼저. 백업.
3. 코드 올리기 → `php bin/migrate.php`로 상태와 사전 점검을 봄 → `--apply` (운영은 확인 옵션과 승인).
4. `GET /api/v1/health`가 `9.0.0`. 기존 기능 점검 ([TEST_PLAN](TEST_PLAN.md) 13.4, 14.5). **여기까지는 플레이어에게 켜진 것이 없음.**
5. 관리자 계정에 새 역할 배정 (콘텐츠 제작 `content` 등 — [ADMIN_SYSTEM](ADMIN_SYSTEM.md) 12.2).
6. 실시간 서버: 런타임 설치 → 서명 키를 두 곳에 넣음 → 띄움 → `/health` → 웹 서버의 WebSocket 중계 → `REALTIME_URL`.
7. 스테이징에서 [TEST_PLAN](TEST_PLAN.md) 15.7의 점검표.
8. 기능을 하나씩 켬 (13.8). 켤 때마다 관리자 첫 화면의 점검과 `system_logs`를 봄.

되돌리기: 기능을 끄는 것이 첫 단계이고 대부분 그것으로 충분합니다 ([DATABASE](DATABASE.md) 9.3).

### 13.6 예약 작업

`bin/tick.php` 하나가 v9.0의 일도 함께 합니다 (`CG\Service\CityOpsTick`). 새로 등록할 작업은 없습니다.

| 일 | 내용 |
|---|---|
| 전입자 집계 | 도시마다 다시 세고 오늘의 기록을 남김. 기준에 닿으면 알림 (같은 기준은 한 번) |
| 재산세 | 정책이 켜져 있을 때만. 한 기간에 한 사람에게 한 번 |
| 참여예산 | 투표 기간이 끝난 제안의 결과 확정 |
| 협동 방어전 | 시간이 지난 대기실·판 닫기 |
| 점검 | 전입자 수, 도시 재정 원장, 협동 방어전의 보상과 공동 예산의 앞뒤. 어긋나면 종료 코드 1과 `system_logs`의 `error` |

예약 작업이 없으면 전입자의 날짜별 기록, 재산세, 투표 확정, 오래된 판 정리가 **돌지 않습니다** (v8.0의 침공 판정과 달리 요청이 올 때 따라잡지 않음). 세금이나 참여예산을 켜기 전에 등록되어 있어야 합니다. 등록은 7장의 승인 항목입니다.

### 13.7 지역 콘텐츠 저장소

상징거리 콘텐츠(Addressables 카탈로그와 번들)는 게임 서버가 아니라 **정적 파일 저장소**에 올립니다. 게임 서버는 "어느 도시의 어느 판을 받는가"만 알려 줍니다 ([CITY_MODELING_PIPELINE](CITY_MODELING_PIPELINE.md) 5장).

- 주소의 앞부분은 `CONTENT_BASE_URL`로 고정하고, 관리자 화면에는 그 아래의 경로와 파일의 해시만 넣습니다. 관리자 계정이 뚫려도 다른 곳의 파일을 내려받게 할 수 없습니다.
- 올린 파일은 **고치지 않습니다** (판마다 다른 경로). 철회는 목록에서 빼는 것이고 파일을 지우지 않습니다.
- 저장소를 어디에 둘지(같은 서버의 정적 경로, 별도의 저장소)는 정해지지 않았습니다. 지금은 올릴 콘텐츠도 없습니다.

### 13.8 승인이 필요한 것

7장의 표에 더합니다. 모두 실행 전에 내용·영향·되돌리는 방법을 알리고 승인받습니다.

| 작업 | 영향 | 되돌리기 |
|---|---|---|
| 마이그레이션 0008~0011 적용 | 새 테이블 21개, 초기값. 기존 테이블은 그대로 | [DATABASE](DATABASE.md) 9.3 |
| v9.0 코드 올리기 | DB 접속의 격리 수준이 바뀜 (13.2). API 버전 `9.0.0` | 이전 코드로 |
| .NET 8 런타임 설치, 실시간 서버 상주, WebSocket 중계 | 서버 자원, 웹 서버 설정 | 중계 설정을 빼고 프로세스를 내림 |
| 협동 방어전 켜기 | 플레이어에게 GC·경험치 보상이 나감 (하루 한도 있음) | 끄기. 나간 보상은 남음 |
| 지방세 켜기 (종류마다) | **플레이어의 GC 가 줄어듦** (거래세는 가격에 포함, 사업세는 보상에서, 재산세는 잔액에서) | 끄기. 걷은 세금은 도시 재정에 남고 돌려주는 기능은 없음 |
| 참여예산 켜기, 도시 재정 집행 | 도시 재정의 GC 가 쓰임 | 집행은 되돌릴 수 없음 |
| 전입자 집계 규칙을 `linked_or_proven`으로 | 게스트 계정도 조건을 채우면 세어짐 → 기준 도달 알림이 생기기 시작 | 규칙을 되돌리면 다음 집계에서 수가 돌아옴. 이미 생긴 알림은 남음 |
| 지역 콘텐츠 배포 | 운영 중인 클라이언트가 새 파일을 받음 | 철회 (일부 배포 → 전체 배포의 순서를 권함) |
| 예약 작업 등록 | 13.6 | 등록 해제 |

### 13.9 로컬에서 시험한 방법 (2026-11-14)

11.5, 12.8과 같은 방법입니다. 이 PC 에 PHP·MySQL 을 새로 설치하지 않았고, 이미 있던 다른 프로젝트의 PHP 7.3.33 과 MariaDB 11.4.13 실행 파일을 **실행만** 했습니다. DB 는 이 저장소의 `server/storage/` 안의 데이터 폴더로 `127.0.0.1:3319`에 따로 띄웠습니다. 그 프로젝트의 데이터·설정·실행 중인 서비스·비밀 값 파일, phpstudy, 운영 서버는 건드리지 않았습니다.

| 항목 | 내용 |
|---|---|
| 서버 테스트 | 테스트 DB 에서 302개 통과 ([TEST_PLAN](TEST_PLAN.md) 15장) |
| 실시간 서버 테스트 | .NET 8 (이 PC 에 이미 있던 SDK). 테스트가 `127.0.0.1`의 빈 포트에 서버를 띄웠다가 내림. 39개 통과 |
| 두 서버를 띄운 확인 | 빈 DB 에 `bin/migrate.php --apply`로 0001~0011을 적용 (사전 점검 "문제 없음", 다시 실행하면 밀린 것 없음). PHP 내장 웹 서버를 `127.0.0.1:8319`에, 실시간 서버를 `127.0.0.1:8390`에 띄움. 서명 키는 그 자리에서 만든 무작위 값을 환경변수로만 줌. HTTP 와 WebSocket 접속 두 개로 47개 확인 통과 ([TEST_PLAN](TEST_PLAN.md) 15.5). `bin/tick.php`의 점검에 문제 없음 |
| 끝난 뒤 | 두 서버와 테스트용 DB 서버를 끄고 시험용 DB 를 지움. `server/storage/` 안에 테스트용 데이터 폴더와 접속 정보 파일, 시험 스크립트가 남음 (git 에 넣지 않음. 지워도 됨) |
| 하지 않은 것 | PHP 8.3, MySQL 8, Linux, Apache·nginx, `wss://`와 프록시 뒤의 WebSocket, 실제 망, 여러 방의 부하, 브라우저로 본 관리자 화면 |

## 14. v10.0 실시간 대시보드

**운영 서버에는 아무것도 올리지 않았고 접속하지도 않았습니다.** 아래는 올리게 될 때의 메모입니다. v10.0만 따로 올리는 것이 아니라 11~13장의 서버 위에 얹히는 것이므로, 그 장들의 확인과 승인이 먼저입니다.

### 14.1 무엇이 더해지는가

| 것 | 내용 |
|---|---|
| API | `GET /api/v1/dashboard/summary` 하나 (읽기 전용, 인증 필요). [API_SPEC](API_SPEC.md) 23장 |
| 관리자 | `/admin/dashboard`, `POST /admin/dashboard/settings` |
| **DB** | **마이그레이션 없음.** 테이블도 열도 더하지 않음. 관리자가 설정을 처음 저장할 때 v8.0의 `game_config`에 `dashboard` 키의 행이 하나 생김 (그 전에는 코드의 기본값) |
| `.env` | 새 설정 없음 |
| 예약 작업 | 없음 |
| 실시간 서버 | 바꾸지 않음. 대시보드는 실시간 서버 없이 동작 |
| `/health`의 버전 | `10.0.0` |

### 14.2 올려도 달라지지 않는 것

- 요약은 읽기만 합니다. 올리는 것만으로 이용자의 GC, 위험도, 재정이 움직이지 않습니다.
- v9.0까지의 경로와 응답은 그대로입니다 (서버 테스트 302개가 그대로 통과).
- 기본 설정에서 개발용 샘플은 꺼져 있습니다 (은행·주식·대출은 "준비 중").

### 14.3 올리기 전에 볼 것

| 것 | 내용 |
|---|---|
| 부하 | 접속자마다 기본 20초에 한 번 요약을 받고, 요약마다 전국 도시의 위험도와 랭킹을 읽음. **캐시가 없음.** 접속자가 많은 서버에서는 먼저 재고, 필요하면 갱신 간격을 늘리거나(관리자 설정, 최대 300초) 전국 부분의 캐시를 만든 뒤에 엶 |
| 클라이언트 | 게임 클라이언트에 HTTP 구현이 없어, 서버에 올려도 지금의 게임은 이 경로를 부르지 않음 |
| 웹 서버의 로그 | 요약의 주소에는 개인 정보가 없음 (인자가 없음). 응답 본문을 기록하는 설정이 있다면 금액이 남으므로 끔 |
| 승인 | 새 경로와 관리자 화면을 여는 것은 기존 서비스에 얹히는 변경이므로 13.8과 같이 사전 승인 |
