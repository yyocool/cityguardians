# PRIVACY_DATA_FLOW — 현실 혜택의 개인정보 흐름

> 기준 v7.0 · 2026-11-13 · 상태: **구현됨, 운영 전.** 암호화·접근 제한·열람 기록·보관 기한 삭제는 서버에 구현되어 로컬 테스트를 통과했습니다. 개인정보 처리방침과 동의서 문구는 **초안**이고, 실제 이용자의 개인정보를 받은 적이 없습니다. 법률 검토가 필요한 질문은 [`REAL_WORLD_REWARDS_POLICY.md`](REAL_WORLD_REWARDS_POLICY.md) 6.2.

CITY PASS 와 GUARDIANS SCHOLARSHIP 이 어떤 정보를 받고, 어디에 두고, 누가 보고, 언제 지우는지 정리합니다. 게임 자체의 개인정보는 [`SECURITY_POLICY.md`](SECURITY_POLICY.md) 8장.

---

## 1. 한눈에 보기

| 서비스 | 받는 개인정보 | 받지 않는 것 |
|---|---|---|
| CITY PASS | **없음.** 게임 계정, 회원번호(서버가 만듦), 관심 지역(고른 것) | 이름, 연락처, 주소, 실제 거주지, 위치 |
| 상점 확인 화면 | 상점 직원의 아이디, 표시 이름(직함), 비밀번호 해시, 접속 주소(IP) | 손님의 정보는 상점에 가지 않는다 |
| 제휴 업체 관리 | 업체 담당자의 이름·전화·이메일 (업무용) | — |
| 장학 신청 | 이름, 태어난 해, 학교급, 학교 이름(선택), 이메일, 전화번호(선택), 신청서, 제출 자료, (미성년자) 보호자의 이름·관계·연락처 | **주민등록번호, 계좌번호, 주소, 생년월일의 월·일, 사진, 파일** |
| 홈페이지 로그인 | 게임 계정에 묶인 일회용 코드와 접속 토큰 (해시만 저장) | 비밀번호, 이메일 |

**게임 닉네임과 실제 개인정보를 묶지 않습니다.** 장학 신청은 계정 번호(`player_id`)로 본인 것임을 구별하지만, 장학 담당·심사위원·지급 담당의 화면에는 닉네임과 게임 기록이 나오지 않습니다. CITY PASS 화면에는 닉네임이 나오지만 실제 개인정보가 없습니다.

## 2. 장학 신청 자료의 분리

지원 자격 확인, 심사, 연락, 보호자 동의에 쓰는 정보를 **목적별로 다른 테이블**에 둡니다.

| 테이블 | 무엇 | 목적 | 암호화 | 볼 수 있는 사람 |
|---|---|---|---|---|
| `scholarship_applications` | 접수 번호, 상태, 학교급, 미성년 여부, 신청서(`form_enc`: 지원 동기, 계획, 확인 문구) | 심사 | 신청서 | 장학 담당, **배정된 심사위원** |
| `scholarship_applicant_profiles` | 이름, 태어난 해, 학교 이름, 이메일, 전화번호 | 자격 확인, 연락 | 이름·학교·이메일·전화 | 장학 담당 (사유를 적고, 열 때마다 기록) |
| `scholarship_documents` | 제출 자료의 제목, 내용 또는 주소 | 심사 | 내용 | 장학 담당, 배정된 심사위원 |
| `scholarship_consents` | 개인정보 동의, 보호자 동의, 보호자의 이름·관계·연락처 | 동의 확인 | 보호자 이름·연락처 | 장학 담당 |
| `scholarship_appeals` | 이의신청 사유 | 이의신청 처리 | 사유 | 처리하는 관리자 |
| `scholarship_reviews`, `scholarship_awards` | 점수, 의견, 결정 | 심사, 선정 | — | 심사위원(자기 것), 장학 담당 |
| `scholarship_disbursement_records` | 지원 방식, 내용, 금액, 상태, 문서 번호 | 지급 상태 | — | 지급 담당 (접수 번호로만 보임) |

- 심사위원 화면은 `scholarship_applicant_profiles` 를 읽지 않습니다. 지원서는 접수 번호와 학교급으로만 보입니다.
- 태어난 해는 나이 판단에 쓰려고 평문 숫자로 둡니다 (연도만으로는 사람을 가려낼 수 없습니다). 보관 기한이 지나면 지웁니다.
- 제출 자료를 주소(URL)로 낸 경우 그 주소는 암호화하지 않습니다. `https://` 만 받습니다.
- 지급 기록에는 계좌번호를 담는 열이 없습니다. 실제 지급에 필요한 정보는 이 시스템 밖의 승인된 절차에서 따로 받아야 합니다.

## 3. 흐름

```
[신청자: 홈페이지]                                   [서버]
 신청서 + 개인정보 ───HTTPS──→ 검증 → 암호화(AES-256-GCM) → DB (목적별 테이블)
 개인정보 동의(버전 기록) ──────────────────────────→ scholarship_consents

[보호자: 일회용 주소]
 학생 이름·프로그램·수집 항목을 봄 → 이름을 적고 동의 ─→ consents (주소의 해시는 지움)

[장학 담당: 관리자 화면, 2단계 인증]
 신청 목록 (개인정보 없음) → 신청서 열람 (기록) → 개인정보 열람 (사유 + 기록) → 보호자 확인 → 자격 확인

[심사위원: 관리자 화면]
 배정된 지원서만: 접수 번호, 학교급, 신청서, 제출 자료 (열람 기록) → 평가

[지급 담당]  접수 번호, 지원 내용, 상태만

[예약 작업 bin/tick.php]  보관 기한이 지난 신청의 개인정보를 지움 (5장)
```

게임으로 가는 것: 공고(공개 정보)와 **본인 신청의 상태**(접수 번호, 프로그램 이름, 상태, 결과, 지급 상태)뿐입니다. 신청서의 내용과 개인정보는 게임 API 응답에 없습니다.

밖으로 나가는 것: 없습니다. 서버는 메일·문자를 보내지 않고, 외부 서비스에 개인정보를 넘기지 않습니다. 홈페이지와 관리자 화면은 외부 스크립트·글꼴·분석 도구를 쓰지 않습니다.

## 4. 암호화

| 항목 | 내용 |
|---|---|
| 방식 | AES-256-GCM (`server/src/Infra/Crypto.php`). 값마다 새 IV(12바이트), 인증 태그 16바이트 |
| 저장 형식 | `v1:` + base64(IV + 태그 + 암호문) |
| 용도 묶기 | 값마다 용도 이름(`profile.name`, `guardian.contact`, `application.form` …)을 함께 인증한다. 한 열의 암호문을 다른 열에 옮겨 넣으면 풀리지 않는다 |
| 키 | 서버의 환경 설정 `DATA_KEY` (base64 로 적은 32바이트). `php bin/new-data-key.php` 로 만든다. **저장소·문서·채팅에 적지 않는다** |
| 키가 없으면 | 장학 신청 접수 기능을 켤 수 없고, 신청이 거절된다. 평문으로 저장하는 길이 없다 |
| 키를 잃으면 | 저장된 신청서와 개인정보를 읽을 수 없다. DB 백업과 **다른 곳에** 따로 보관해야 한다 |
| 키가 새면 | 암호화가 소용없다. DB 덤프와 키가 같은 곳에 있으면 안 된다 |

암호화하지 않고 **해시만** 저장하는 것: 홈페이지 로그인 코드와 접속 토큰, 쿠폰의 일회용 코드, 보호자 확인 주소의 값, 상점·관리자 비밀번호(`password_hash`).

**없는 것**: 키 교체(회전) 도구가 없습니다. 형식에 버전(`v1:`)을 두었지만, 새 키로 다시 암호화하는 절차는 만들지 않았습니다. 운영 전에 필요합니다. DB 서버의 저장 장치 암호화와 백업 암호화는 이 저장소의 범위 밖입니다.

## 5. 보관 기간과 삭제

| 자료 | 보관 | 지우는 방법 |
|---|---|---|
| 선정되지 않은 신청 (예비 선정 포함) | 결과 통지 뒤 180일 (프로그램마다 30~365일) | 예약 작업 |
| 선정된 신청 | 결과 통지 뒤 1825일 = 5년 (30~1825일) | 예약 작업 |
| 자격에 해당하지 않은 신청 | 결정 뒤 180일 | 예약 작업 |
| 철회한 신청 | 철회 뒤 30일 | 예약 작업 |
| 결과 없이 보관 처리된 프로그램의 신청 | 보관 처리 뒤 180일 | 예약 작업 |
| 홈페이지 로그인 코드, 접속 기록 | 만료 뒤 7일 | 예약 작업 (행 삭제) |
| 상점 접속 기록 | 만료 뒤 7일 | 예약 작업 (행 삭제) |
| 쿠폰, 사용 기록, 거래 로그 | 정해지지 않음 (개인정보 없음: 계정 번호와 회원번호) | — |
| 감사 로그 | 정해지지 않음 | — |

예약 작업(`php bin/tick.php`)이 기한(`purge_after`)이 지난 신청에서 지우는 것: 신청서, 자격 메모, 이름, 태어난 해, 학교 이름, 이메일, 전화번호, 제출 자료의 제목·내용·주소, 보호자의 이름·연락처, 보호자 확인 메모, 이의신청 사유, 심사 의견.

남는 것: 접수 번호, 프로그램, 상태, 결과, 점수, 날짜, 계정 번호. 통계와 감사에 쓰려는 것입니다. 계정 번호가 남으므로 완전한 익명 자료는 아닙니다.

- 기능이 꺼져 있어도 예약 작업은 돕니다 (꺼진 뒤에도 보관 기간은 흐릅니다).
- 이의신청이 받아들여져 다시 심사하게 되면 삭제 기한이 풀리고, 다시 통지할 때 새로 정해집니다.
- **운영 서버에 예약 작업을 등록하는 것은 사전 승인이 필요합니다.** 등록하지 않으면 삭제가 일어나지 않습니다.
- 보관 기간의 숫자(180일, 5년)는 개발 단계의 기본값입니다. 법령(장학금 지급 증빙의 보관 의무 등)에 맞는지 검토가 필요합니다.

**없는 것**: 본인이 "지금 지워 달라"고 요청하는 화면이 없습니다 (철회하면 30일 뒤에 지워집니다). 본인이 낸 신청서를 다시 내려받는 기능, CITY PASS 탈퇴 화면도 없습니다. 운영 전에 열람·정정·삭제 요청을 받는 절차가 필요합니다.

## 6. 접근 권한

| 역할 | CITY PASS | 장학 신청서 | 장학 개인정보 | 감사 로그 |
|---|---|---|---|---|
| CITY PASS 담당 (`pass_manager`) | 관리 | ✕ | ✕ | ✕ |
| 장학 담당 (`sch_manager`) | ✕ | 열람 (기록) | 열람 (사유 + 기록) | ✕ |
| 심사위원 (`reviewer`) | ✕ | 배정된 것만 (기록) | ✕ | ✕ |
| 지급 담당 (`finance`) | ✕ | ✕ | ✕ | ✕ |
| 준법·개인정보 담당 (`compliance`) | 보기 | 목록만 | ✕ | 열람 |
| 최고 관리자 (`super`) | 관리 | 열람 (기록) | 열람 (사유 + 기록) | 열람 |
| 게임 운영 역할 (`operator`, `balance`, `support`, `viewer`) | ✕ | ✕ | ✕ | ✕ |

- 개인정보 열람은 **기록을 먼저 남기고** 엽니다. 기록하지 못하면 열리지 않습니다. 기록에는 누가, 언제, 어느 신청을, 왜, 어느 주소에서 열었는지가 남습니다 (`pii.view`).
- 관리자 화면 "장학: 개인정보 접근 로그"에서 준법 담당이 봅니다.
- 관리자 계정은 2단계 인증이 필수이고, 서버에서 명령줄 도구로만 만듭니다 ([`ADMIN_SYSTEM.md`](ADMIN_SYSTEM.md) 2장).
- 상점 계정은 자기 업체(지점)의 쿠폰 처리 내역만 봅니다. 손님의 닉네임·회원번호·계정은 상점 화면에 나오지 않습니다.
- DB 계정의 분리(개인정보 테이블에 접근하는 DB 사용자를 따로 두기)는 **하지 않았습니다.** 애플리케이션은 DB 계정 하나로 접속합니다. 접근 제한은 애플리케이션의 역할과 열 암호화로 합니다. 운영 DB 에서 개인정보 테이블의 권한을 나누려면 [`DATABASE.md`](DATABASE.md) 6장의 방법으로 따로 설정해야 합니다.

## 7. QR 과 코드

- 쿠폰 QR 에는 5분짜리 일회용 코드만 있습니다. 회원번호·닉네임·쿠폰 번호·계정 번호가 없습니다 ([`COUPON_SYSTEM.md`](COUPON_SYSTEM.md) 4장).
- 홈페이지 로그인 코드는 5분, 한 번, 한 계정에 하나만 살아 있습니다.
- 보호자 확인 주소는 추측할 수 없는 값이고, 동의하면 죽습니다. 주소에는 학생의 정보가 들어 있지 않습니다.

## 8. 로그에 남기지 않는 것

- 서버의 시스템 로그와 감사 로그에는 신청서의 내용, 이름, 연락처를 적지 않습니다. 감사 로그의 `detail` 에는 사유, 상태 변화, 번호만 들어갑니다.
- 접속 주소(IP)는 감사 로그와 상점 계정 기록에 남습니다 (부정 사용 추적용). 보관 기간은 정해지지 않았습니다.

## 9. 남은 일 (운영 전)

1. 개인정보 처리방침, 수집·이용 동의서, 보호자 동의서의 문구 확정 (법률 검토).
2. 만 14세 미만의 법정대리인 동의 방식 확정.
3. 개인정보 보호책임자 지정, 열람·정정·삭제 요청 창구.
4. 암호화 키의 보관·교체 절차, DB 백업의 암호화.
5. 심사위원(외부 위원)에게 신청서를 보여 주는 것의 법적 성격 (위탁 / 제3자 제공) 과 서약서.
6. 보관 기간의 확정, 쿠폰·감사 로그의 보관 기간.
7. 운영 DB 에서의 권한 분리, 접근 기록의 정기 점검.
