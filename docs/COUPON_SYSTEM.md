# COUPON_SYSTEM — 쿠폰

> 기준 v7.0 · 2026-11-13 · 상태: **구현됨, 운영 전.** 서버는 로컬 테스트 DB에서 테스트 통과. 게임의 QR 화면은 작성해 형식 검사만 함 (QR 을 만드는 코드는 규칙 테스트로 검증). 쿠폰 기능은 꺼진 채로 설치되고, **실사용자에게 발급한 쿠폰은 없습니다.**

CITY PASS 쿠폰은 제휴 상점의 혜택 하나를 한 번 쓸 수 있는 표입니다. 값을 치르지 않고 받고, 상점이 서버에서 확인해야 쓰입니다.

관련 문서: [`CITY_PASS_SYSTEM.md`](CITY_PASS_SYSTEM.md), [`PARTNER_MERCHANT_SYSTEM.md`](PARTNER_MERCHANT_SYSTEM.md), [`CITY_PASS_API.md`](CITY_PASS_API.md), [`REAL_WORLD_REWARDS_POLICY.md`](REAL_WORLD_REWARDS_POLICY.md)

---

## 1. 원칙

| 지시서 | 지키는 방법 |
|---|---|
| 쿠폰 발급은 GC 나 전투 보상과 연동하지 않는다 | 발급 사유(`issue_reason`)는 `membership`, `promotion`, `partner_condition` 셋뿐이다. 발급 코드는 지갑·원장·전투 테이블을 읽지도 쓰지도 않는다 (줄은 멤버십 행에서 선다). 테스트가 발급·사용 앞뒤의 GC 와 원장 행 수를 비교한다 |
| QR 코드에 개인정보를 넣지 않는다 | QR 에는 5분짜리 일회용 코드만 들어간다 (4장). 회원번호, 닉네임, 쿠폰 번호, 계정 번호가 없다 |
| 검증과 사용 처리는 서버에서 한다 | 이용자의 기기에는 쿠폰을 "사용함"으로 만드는 요청이 없다. 상점 확인 화면이 서버에 요청하고, 서버가 상태를 바꾼다 (5장) |
| 같은 쿠폰이 두 번 쓰이지 않는다 | 원자적 상태 변경 + 유일 제약 + 거래 로그 (3장) |

## 2. 쿠폰의 한살이

```
        발급 (claim)                    사용 처리 (상점)
혜택 ───────────────→ issued ───────────────────────────→ redeemed
                        │  ↑ 제시 (present): 일회용 코드를 만든다. 상태는 그대로다
                        ├── 유효기간이 지남 ──→ expired
                        └── 관리자가 취소 ───→ cancelled
```

| 단계 | 규칙 |
|---|---|
| 발급 | CITY PASS 회원이고, 혜택이 밖에 보이는 상태이며, 내 한도(`per_member_limit`)와 전체 수량(`total_limit`)이 남아 있을 때. 같은 요청 번호(`Idempotency-Key`)로 다시 보내면 처음 응답을 돌려준다 (두 장이 생기지 않는다) |
| 유효기간 | 받은 때 + `coupon_valid_days`. 혜택의 종료일을 넘지 않는다 |
| 목록 | 본인만 본다. 남의 쿠폰 번호를 넣으면 "없는 쿠폰"이다 |
| 만료 | 유효기간이 지나면 조회할 때 바로 만료로 보이고, 예약 작업(`bin/tick.php`)이 DB 의 상태도 `expired` 로 적는다 |
| 취소 | 관리자(`pass.manage`)가 쓰지 않은 쿠폰만, 사유를 적고 취소한다. 취소된 쿠폰은 한도 계산에서 빠진다 |

## 3. 중복 사용 방지

사용 처리는 한 거래 안에서 다음을 합니다 (`MerchantPortal::redeem`).

1. 코드의 해시로 쿠폰 행을 찾아 **잠급니다** (`SELECT … FOR UPDATE`).
2. **조건을 붙여 상태를 바꿉니다.** 한 행이 바뀌었을 때만 성공입니다.
   ```sql
   UPDATE benefit_coupons SET status = 'redeemed', redeemed_at = ?, present_code_hash = NULL, present_expires_at = NULL
    WHERE id = ? AND status = 'issued' AND present_code_hash = ? AND present_expires_at > ? AND expires_at > ?
   ```
3. `coupon_redemptions` 에 사용 기록을 넣습니다. `coupon_id` 가 **유일 키**라서, 어떤 이유로든 두 번째 기록은 들어가지 못합니다.
4. `coupon_events` (거래 로그) 에 `redeemed` 를 적습니다.

성공하면 일회용 코드의 해시를 지우므로 같은 코드는 다시 쓸 수 없습니다. 테스트(`CityPassTest::testConcurrentRedeemLosesTheRace`)는 같은 조건부 `UPDATE`를 두 번 실행해 첫 번째만 1행을 바꾸고 두 번째는 0행을 바꾸는지, 그 뒤의 사용 처리가 거절되는지를 확인합니다. **실제로 두 접속을 동시에 띄워 경쟁시키는 부하 테스트는 하지 않았습니다.**

**거래 로그** `coupon_events` 는 추가만 합니다: `issued`, `presented`, `verify_failed`, `redeemed`, `expired`, `cancelled`. 실패한 시도는 거래가 되돌려진 뒤에 따로 적습니다 (되돌려져도 시도는 남아야 합니다).

## 4. 제시 코드와 QR

쿠폰을 상점에 보여 줄 때마다 서버가 **일회용 코드**를 새로 만듭니다.

| 항목 | 내용 |
|---|---|
| 모양 | `XXXXX-XXXXX` (10자). 헷갈리는 글자(0·O, 1·I·L)가 없는 31자에서 고른다 |
| 수명 | 5분. 쿠폰의 유효기간이 그보다 먼저 끝나면 거기까지 |
| 하나만 | 다시 만들면 앞의 코드는 못 쓴다 |
| 저장 | 서버에는 SHA-256 해시만 남는다 (`present_code_hash`) |
| 횟수 | 한 사람이 10분에 30번까지 |
| 쿠폰의 상태 | 코드를 만든다고 바뀌지 않는다. 5분이 지나면 코드만 죽고 쿠폰은 그대로다 |

**QR 에 들어가는 글자**는 서버가 정합니다 (`qrPayload`).

- `PUBLIC_BASE_URL` 이 설정되어 있으면 `https://…/merchant/redeem?code=XXXXX-XXXXX` — 직원이 휴대전화 카메라로 찍으면 상점 확인 화면이 열립니다. 로그인해야 하고, **열기만 해서는 쓰이지 않습니다** (주소로 들어온 코드는 확인 화면을 보여 줄 뿐이고, 사용 처리는 버튼을 눌러야 합니다).
- 없으면 `CGPASS:XXXXX-XXXXX`.

어느 쪽이든 그 일회용 코드뿐입니다. 게임은 서버가 보낸 글을 그대로 믿지 않고 한 번 더 확인합니다 (`BenefitRules.SafeQrText`): `CGPASS:코드` 이거나, `https://` 로 시작하고 `?code=코드` 로 끝나는 주소(물음표 하나, `#`·`@`·빈칸·한글 없음, 213바이트 이하)이고, 회원번호가 들어 있지 않으며 닉네임과 같은 마디가 없을 때만 씁니다. 어긋나면 `CGPASS:코드` 만 그립니다.

**게임의 QR 화면** (`CouponPresenter`, `QrPanel`):

- QR 은 게임 안에서 만듭니다 (`Domain/QrCode.cs`: 바이트 모드, 오류 정정 M, 버전 1~10). 외부 서비스에 코드를 보내지 않습니다.
- 흰 바탕에 둘레 4칸의 빈 영역을 두고, 한 칸을 한 점으로 그려 번지지 않게 늘립니다.
- QR 아래에 코드를 글자로도 보여 줍니다 (카메라가 없으면 직원이 손으로 넣습니다). 남은 시간이 줄어들고, 0이 되면 화면이 닫히며 "쿠폰은 그대로 있어요"라고 알립니다.
- E 로 닫으면 그림과 코드를 화면 상태에 남기지 않고, 쿠폰 목록을 서버에서 다시 받아 옵니다 (상점이 처리했으면 "사용함"으로 보입니다).
- 장면이 바뀌면 조용히 닫힙니다.

QR 을 만드는 코드는 두 가지로 확인했습니다 (`QrCodeTests` 18개): 널리 쓰이는 구현(Node `qrcode` 1.5.4)이 만든 그림과 **칸 하나하나가 같은지**(버전 1~10), 그리고 만든 그림을 다시 읽어 원래 글자가 나오는지.

> 실제 휴대전화 카메라로 게임 화면의 QR 을 찍어 본 적은 없습니다 (Unity 에서 실행하지 못했습니다). 운영 전에 여러 기기로 확인해야 합니다.

## 5. 상점 확인 화면

경로는 `{설치 경로}/merchant` 입니다. 자바스크립트 없이 동작합니다. 계정과 접근 범위는 [`PARTNER_MERCHANT_SYSTEM.md`](PARTNER_MERCHANT_SYSTEM.md) 5장.

| 경로 | 내용 |
|---|---|
| `/merchant/login` | 상점 관리자 로그인 |
| `/merchant/password` | 비밀번호 바꾸기 (처음 로그인하면 여기로 온다) |
| `/merchant` | 첫 화면: 쿠폰 코드 넣기, 오늘 처리한 수 |
| `/merchant/redeem` | 쿠폰 코드 확인. QR 로 들어오면 코드가 채워져 있다 |
| `POST /merchant/verify` | 유효성 검증: 혜택, 할인 내용, 이용 조건, 쿠폰과 코드의 만료 시각을 보여 준다. **손님의 정보는 보여 주지 않는다** |
| `POST /merchant/redeem` | 사용 처리. 본사 계정이고 지점이 여럿이면 지점을 고른다 |
| `/merchant/history` | 이용 내역: 처리한 시각, 혜택, 지점, 처리한 직원 |
| `/merchant/stats` | 통계: 오늘, 최근 7일, 전체, 혜택별, 최근 14일의 날짜별. 본사 계정에는 혜택별 발급 수 |

확인과 사용 처리가 거절되는 경우:

| 경우 | 화면에 나오는 말 |
|---|---|
| 모르는 코드 / 다른 업체의 쿠폰 / 이미 쓴 쿠폰 | "쓸 수 있는 쿠폰을 찾지 못했습니다" (구별하지 않는다: 코드가 맞는지 떠보지 못하게) |
| 코드의 5분이 지남 | "코드의 시간이 지났습니다. 손님에게 코드를 새로 받아 주세요" |
| 쿠폰의 유효기간이 지남 | "유효기간이 지난 쿠폰입니다" |
| 다른 지점의 쿠폰 (지점 계정) | "이 지점에서는 쓸 수 없는 쿠폰입니다" |
| 10분 안에 10번 틀림 | 10분 동안 처리할 수 없다 |
| 쿠폰 기능이 꺼짐, 업체가 승인 상태가 아님, 비밀번호를 아직 바꾸지 않음 | 처리할 수 없다 |

## 6. 확인한 것

- 서버 `CityPassTest` 21개: 발급 조건과 한도, 멱등, 수량 소진, 코드의 수명과 교체, 사용 처리와 중복 방지, 경쟁에서 진 쪽의 처리(순서대로 흉내 낸 것), 다른 업체·다른 지점의 계정, 만료, 취소, 기능이 꺼졌을 때, GC 와 원장이 그대로인지.
- 서버 `BenefitWebTest`: 상점 화면의 로그인, 잠금, CSRF, 비밀번호 바꾸기, QR 주소로 열기만 해서는 쓰이지 않는지.
- 클라이언트 `LocalMockBackendBenefitTests`: 모의 서버가 같은 규칙을 지키는지.

## 7. 한계

- 쿠폰 양도, 선물하기가 없습니다. 코드를 다른 사람에게 보여 주는 것을 기술로 막지는 못합니다 (5분의 수명과 부정 사용 탐지로 줄일 뿐입니다).
- 상점이 인터넷에 연결되어 있어야 합니다 (오프라인 확인 없음).
- 사용 처리의 취소(잘못 처리했을 때 되돌리기)가 없습니다. 운영팀이 수동으로 다뤄야 합니다.
- 홈페이지는 코드를 글자로만 보여 줍니다 (QR 그림 없음).
