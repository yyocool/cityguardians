| 항목 | 선택 | 이유 |

| 캐릭터·환경 | 기본 도형과 코드로 조립한 블록 메시 | 외부 에셋 없이 시작, 고유 디자인, 나중에 교체 가능 |

## 4. 서버 없이도 진행하는 방법

서버 접속과 PHP 전환이 정해지기 전에도 클라이언트 작업이 멈추지 않도록, 서버 통신을 인터페이스(`IGameBackend`) 뒤에 둡니다.

| 구현 | 용도 |
|---|---|
| 로컬 모의 구현 | 서버 없이 Unity 안에서 같은 규칙으로 동작. Phase 1 개발과 자동 테스트용 |
| HTTP 구현 | 실제 PHP API 호출 |

모의 구현은 개발용이며 공개 빌드에는 들어가지 않습니다. 보상과 금융의 실제 규칙은 서버 코드가 기준입니다.

## 5. 단계별 계획

각 단계는 "끝났다고 볼 조건"을 통과해야 다음으로 넘어갑니다. 서버 작업은 Phase 1부터 나란히 진행합니다.

### Phase 0 — 준비

| 작업 | 승인 필요 |
|---|---|
| git 저장소 초기화, `.gitignore` | — |
| 서버 읽기 전용 조사 ([SERVER_DEPLOYMENT](SERVER_DEPLOYMENT.md) 2장) | 접속 정보 제공 |
| 기존 v1 소스와 DB 구조 확보, 이 설계와 대조 | 접속 정보 제공 |
| 현재 서버 상태 전체 백업 | 예 |
| 로컬 PHP 8.3 / MySQL 8 설치 | 예 |
| 문서 갱신: DATABASE, API_SPEC, SERVER_DEPLOYMENT를 실제 구조에 맞춤 | — |

끝난 조건: 서버의 실제 구조를 알고, PHP 전환 방법이 정해지고, 첫 백업이 있다.

### Phase 1 — PC 3D 기본 플레이

| 클라이언트 | 서버 (병행) |
|---|---|
| Unity 프로젝트, 계층 구조, 입력 추상화 | 로컬 환경에 PHP 애플리케이션 뼈대 |
| 블록형 캐릭터, 이동·점프, 3인칭 카메라 | 마이그레이션 체계, 핵심 테이블 |
| 개인 방 (기본 가구, 컴퓨터, 문) | 게스트 생성, 토큰, `/me`, `/defs` |
| 대표 도시 (광장, 주거, 상점, 은행, 전투 구역) | 지갑, 원장, 중복 방지 |
| NPC (보리, 도담, 방어대장, 주민) 와 대화 | 사냥 보상 검증과 지급 |
| 오작동 로봇·기계 곤충, 근접 무기, 체력, 보상 연출 | 적·아이템 정의 |
| 첫 플레이 연출 | — |

끝난 조건: 실행 → 방 → 도시 → NPC 대화 → 로봇 사냥 → GC 획득이 끊기지 않는다. 처음 해 보는 사람이 설명 없이 첫 로봇을 쓰러뜨린다. 재실행하면 GC와 레벨이 남아 있다 (로컬 서버 기준).

**이 단계의 목적은 "재미가 있는가"를 확인하는 것입니다.** 움직이고 때리는 감각이 좋지 않으면 다음 단계로 가지 않고 여기서 다듬습니다.

#### Phase 1 구현 기록 (2026-11-13, 클라이언트)

구현한 것: 계층 구조(`CG.Domain` → `CG.Services` → `CG.Input` → `CG.Gameplay` → `CG.UI`), 블록형 캐릭터와 절차적 동작, 내 방, 해운대구 도시(광장·집·상점·은행·주민센터·방어기지·전투 구역 2곳·해변), NPC 6명과 대화, 오작동 로봇·기계 곤충, 방어 배턴, 사냥 보상(모의 서버 검증·원장), 첫 플레이 안내, 저장과 복구.

자동으로 확인한 것 (`tools/unity/run-unity.ps1`):

| 확인 | 결과 |
|---|---|
| EditMode 테스트 (규칙 계산, 적 상태 기계, 모의 서버) | 36개 통과 |
| PlayMode 테스트 — 방 → 컴퓨터 → 문 → 도시 → 첫 로봇 → 도담 보상 → 방어대장 → 전투 구역 사냥 → 원장 점검 → 껐다 켜기 | 통과. 입력은 `ScriptedInput` 이 대신함 |
| PlayMode 테스트 — 게스트 저장 파일이 깨졌을 때 묻고 나서만 새로 시작, 옛 파일 보관 | 통과 |
| Windows 개발 빌드 | 성공. 화면 없이 실행해 시작 과정에 예외가 없음을 확인 |

아직 확인하지 못한 것:

- **사람이 직접 해 본 조작감과 재미.** 자동 테스트는 흐름이 끊기지 않는지만 봅니다. "처음 해 보는 사람이 설명 없이 첫 로봇을 쓰러뜨린다"는 끝난 조건은 실제 플레이로만 확인할 수 있습니다.
- 빌드된 실행 파일의 화면 (창을 띄워 보지 않음), 마우스 조작, 소리, 전체화면·창 전환.
- 서버. Phase 1의 서버 쪽 항목은 시작하지 않았습니다.

설계 문서와 다르게 구현한 것 (각 문서에도 반영):

| 항목 | 설계 | 구현 | 이유 |
|---|---|---|---|
| 사냥 보고 간격 | 10초 | 3초 (집 앞 첫 전투 구역은 0.2초) | 보상이 확정되는 것이 바로 보여야 함 |
| 첫 전투 보호 | 체력 30% 아래면 보리가 주의를 끎 | 첫 로봇은 체력을 20% 아래로 깎지 못함 | 보리는 방에 있어 도시 전투에 낄 수 없음 |
| 목표 한 줄 | 방을 나선 뒤 표시 | 방에서부터 표시 | 처음에 무엇을 할지 알려 줄 수단이 필요 |
| 방 카메라 | 좁은 곳에서 거리 자동 조정 | 벽이 안쪽에서만 보이는 "인형의 집" 방식 | 좁은 방에서 카메라가 벽에 끼지 않음 |
| 전입신고 안내 | 예 / 나중에 버튼 | 방어대장이 대화에서 한 번 권유만 함 | 전입신고 기능 자체가 아직 없음. 버튼은 그 기능과 함께 추가 (→ Phase 2 구현 기록 ②에서 주민센터의 선택 메뉴로 구현) |
| 일시정지·대화 조작 | (미정) | 키보드만 (Esc, E, Space). 화면 버튼 없음 | Phase 1 범위. 모바일 확장 때 버튼 필요 |
| 임무 보상 API | 없음 | `POST /quests/{code}/claim` 추가 | 첫 구조 임무 보상 100 GC를 서버가 지급해야 함 |
| 도시를 지키는 NPC (함께 싸움) | NPC_SYSTEM | Phase 1에서 뺌 | 범위 축소 |
| 상점·은행·주민센터 | Phase 3~ | 건물과 NPC만 있고 "준비 중" 안내 | 계획대로 |

알아 둘 것:

- 게스트 비밀키는 모의 단계에서 저장 파일에 평문으로 둡니다. 실제 서버를 붙일 때 [SECURITY_POLICY](SECURITY_POLICY.md)에 맞춰 바꿉니다.
- `ProjectSettings` 의 회사 이름 `CityGuardians` 는 임시값입니다. 저장 폴더 경로에 들어가므로 출시 전에 확정해야 합니다.
- 캐릭터가 벽을 등져 카메라가 1.3 m 안으로 당겨지면 캐릭터를 그리지 않습니다 (머리가 화면을 가리지 않게).

#### Phase 2 구현 기록 ① 방어전 (2026-11-13, 클라이언트)

Phase 2는 재미의 중심인 방어전부터 만들었습니다. 이 기록을 쓴 시점에는 지도 화면과 전입신고가 없어 끝난 조건 중 "방어전 승리 → 보상"까지만 됐습니다. 나머지는 아래 "구현 기록 ②"에 있습니다.

구현한 것: 도시 방어기지의 출동 게이트와 선택 메뉴, 방어전 전장 "외곽 1구역"(장면 `Defense`), 설치 자리 6곳, 기관총 타워·폭발 타워와 전투 중 강화, 웨이브 5개, 도시 방어 체력, 건설 메카, NPC 방어대원 2명, 승리·패배·후퇴 결과 화면, 전투 결과 검증과 보상(모의 서버), 폭발 타워 해금(500 GC). 자세한 내용은 [TOWER_DEFENSE](TOWER_DEFENSE.md).

자동으로 확인한 것:

| 확인 | 결과 |

#### Phase 3 구현 기록 ② (2026-11-13, 클라이언트)

Phase 3의 나머지를 만들었습니다: 방어구, 의상, 가구와 방 꾸미기, 정기예금, 되팔기. 이율은 하루 1%, 한도 10,000 GC로 바꿨습니다 (7장의 결정). 서버 쪽은 여전히 모의 서버에만 있습니다.

구현한 것:

- **방어구.** 가디언 헬멧(150 GC, 받는 피해 -10%), 가디언 조끼(250 GC, -20%). 미소 상점에서 삽니다. 방어는 뺄셈이 아니라 비율입니다. [COMBAT_SYSTEM](COMBAT_SYSTEM.md) 4장.
- **의상과 입은 모습.** 파도 모자, 토끼 머리띠, 해님 후드티, 별 티셔츠 (80 ~ 120 GC, 능력치 없음). 입으면 캐릭터의 모습이 바뀝니다. 가방(I)이나 내 방 옷장에서 갈아입습니다. [CHARACTER_SYSTEM](CHARACTER_SYSTEM.md) 8장.
- **알록달록 가게.** 광장 남동쪽의 새 건물과 NPC 한아름. 옷과 가구를 팝니다. 첫 화면은 "옷 사기 / 가구 사기 / 물건 팔기".
- **가구와 방 꾸미기.** 화분, 쿠션, 조명, 책장, 소파 (80 ~ 400 GC). 방에서 F를 누르고 가구를 들고 걸어 다니며 놓습니다. 놓기, 돌리기, 옮기기, 넣어 두기. 놓을 수 있는 자리는 서버가 검사합니다. [ROOM_SYSTEM](ROOM_SYSTEM.md) 8장.
- **되팔기.** 산 값의 30%. 그 물건을 파는 가게에서, 값을 먼저 보여 주고 한 번 더 묻습니다. [ITEM_SYSTEM](ITEM_SYSTEM.md) 7.3, 12장.
- **정기예금.** 7일(이자 10%)과 30일(이자 50%). 지갑에서 가입, 만기에 통장으로, 중간에 찾으면 원금만. [ECONOMY_SYSTEM](ECONOMY_SYSTEM.md) 10장.
- **화면 기반.** 선택 메뉴가 여섯 줄까지 (숫자 1~6). 안내판의 글이 넘치면 글자를 줄여 맞춥니다.

Phase 4에 넘기는 조건: 대출 이율은 보통예금 이율(하루 1%)보다 높아야 합니다. 낮으면 빌려서 예금하는 것만으로 돈이 늘어납니다 ([ECONOMY_SYSTEM](ECONOMY_SYSTEM.md) 9.5). 정기예금(30일 50% = 하루 약 1.67%)까지 따지면 하루 2% 이상이어야 합니다.

만들면서 고친 것:

- **든 가구의 방향.** 든 가구의 앞면이 언제나 나를 보고 나와 함께 돌게 했습니다. 벽을 보고 서면 등받이가 벽 쪽으로 가므로 대부분 R이 필요 없습니다. 옮기는 가구는 놓여 있던 방향 그대로 들립니다.
- **거래 내역이 안내판을 넘쳤습니다** (캡처에서 발견). 정기예금으로 줄이 길어져 글이 접히면서 제목과 닫기 안내를 덮었습니다. 줄을 접지 않고, 넘치면 글자 크기를 줄입니다. 테스트가 넘치지 않는지 확인합니다.
- **방의 창문이 카메라를 가렸습니다** (캡처에서 발견). 북쪽 벽의 창문과 서쪽 벽의 거울이 두께가 있는 상자여서, 카메라가 벽 밖으로 나가면 큰 흰 네모로 보였습니다. 방 안쪽에서만 보이는 판으로 바꿨습니다.
- **사냥 보상의 수리 키트가 테스트의 가방 줄 수를 바꿨습니다.** 테스트가 드롭 확률을 0으로 두고 시작합니다 (게임은 바꾸지 않음).
- **상점 테스트가 전체 실행에서 한 번 실패했습니다.** "겨눌 적이 없으면 조준 표시가 없다"를, 전투 구역에서 광장으로 순간 이동한 바로 그 프레임에 확인하고 있었습니다. 조준 표시는 프레임의 끝에 갱신됩니다. 테스트가 한 프레임 뒤에 확인하게 했습니다 (게임은 바꾸지 않음). 고친 뒤 전체 15개 통과.

| 대표 도시 | **부산광역시 해운대구** |
| 지도 경계 데이터 | 공공 데이터 ([MAP_SYSTEM](MAP_SYSTEM.md) 2장) |
| 보통예금 이율 (12번) | **하루 1%, 이자 한도 10,000 GC** (처음 값은 하루 0.1%, 한도 100,000 GC) |

## 8. 위험

| 위험 | 대응 |
|---|---|
| 범위가 넓다 (RPG + 방어 + 금융 + 커뮤니티) | 1차는 17단계에만 집중. 나머지는 DB·API 자리만 |
| 재미가 확인되기 전에 시스템이 늘어난다 | Phase 1에서 조작감과 전투의 재미를 먼저 확인 |
| 기존 v1과 설계가 어긋난다 | Phase 0에서 실제 구조 확인 후 문서 갱신. 기존 것을 보존하는 방향 |
| PHP 전환으로 기존 사이트가 깨진다 | 스테이징에서 먼저 확인, 백업, 되돌리는 방법 준비 |
| 그림·모델 자원이 부족하다 | 도형으로 조립하는 블록 스타일로 시작 |
| 미성년자 대상 금융·채팅 규정 | 해당 단계 전 전문가 검토 |
| 지도 데이터 이용 조건 | 구현 전 확인함 (공공누리 제1유형 + CC BY 4.0, 출처 표시). 전문가 검토는 빌드 공개 전에 ([MAP_SYSTEM](MAP_SYSTEM.md) 2.1) |
| 지역 목록이 운영 DB와 다르다 (230곳 대 229곳, 코드 체계 미확인) | 서버 조사 때 대조. 다르면 대응표를 두거나 지도 데이터를 다시 만듦 ([MAP_SYSTEM](MAP_SYSTEM.md) 2.3) |
| 조작된 클라이언트의 보상 요청 | 서버 검증과 한도 |

## 9. 작업 규칙

- 각 단계의 끝난 조건을 통과한 뒤 다음으로 넘어갑니다.
- 한 번에 하나의 흐름을 끝까지 만듭니다 (화면 → 규칙 → 서버 → 저장).
- 수치는 코드에 박지 않고 정의 데이터에 둡니다.
- 설계가 바뀌면 문서를 함께 고칩니다.
- 기존 서비스에 영향을 주는 변경은 승인을 받습니다.
- 비밀 값을 저장소에 넣지 않습니다.
