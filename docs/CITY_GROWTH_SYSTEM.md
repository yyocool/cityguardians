# CITY_GROWTH_SYSTEM — 도시 성장 (전입자 집계와 확장 단계)

> 기준 v9.0 · 2026-11-14 · 상태: PHP 서버(`CG\Service\Growth`), 관리자 화면, 모의 서버, 게임 화면(작전 본부 → 도시 살림 → 도시 성장) 구현. 서버는 로컬 테스트 DB에서만 돌려 보았고 운영에는 배포하지 않음. Unity 화면은 컴파일 검사만 했고 실행해 보지 못함 · 기준 인원과 수수료는 확정 전의 초기값

## 1. 방향

전국 시·군·구마다 "지금 이 도시에 사는 가디언이 몇 명인가"를 세고, 그 수가 기준에 닿은 도시부터 3D 상징거리를 만들어 엽니다. 어느 도시를 먼저 만들지를 감이 아니라 데이터로 정하기 위한 장치입니다.

지키는 원칙은 다섯 가지입니다.

1. **전입자 수는 서버가 셉니다.** 전입자 수를 받는 API가 없습니다. 클라이언트는 "전입신고를 한다", "이사한다"만 요청합니다.
2. **게스트 계정을 여러 개 만들어도 전입자 수가 늘지 않습니다.** 세는 것은 "유효 전입자"뿐입니다 (2장).
3. **한 계정은 한 도시에만 삽니다.** 주거 도시는 `players.region_id` 하나이고, 이사는 그 값을 옮기는 일입니다. 두 도시에 동시에 세어질 수 없습니다.
4. **기준은 관리자가 바꿉니다.** 인원 기준, 이사 수수료, 세는 규칙 모두 관리자 화면에서 고치고, 사유와 감사 기록이 남습니다.
5. **기준에 닿았다고 저절로 열리지 않습니다.** 기준 도달은 알림을 만들 뿐이고, 실제 3D 콘텐츠는 제작 → 검수 → 배포를 거쳐야 열립니다 ([CITY_MODELING_PIPELINE](CITY_MODELING_PIPELINE.md)).

## 2. 유효 전입자

| 값 | 뜻 | 저장 |
|---|---|---|
| 전입신고를 한 계정 수 | 게스트를 포함해 그 도시에 전입신고를 한 모든 계정. v8.0부터 있던 값 | `regions.resident_count` (그대로), `city_population_stats.registered_residents` |
| **유효 전입자 수** | 아래 규칙으로 인정된 계정만 | `city_population_stats.valid_residents` |
| 누적 유효 전입자 수 | 그 도시에서 유효 전입으로 인정된 적이 있는 계정 수 (이사를 가도 줄지 않음) | `city_resident_marks`의 행 수 → `cumulative_residents` |
| 최근 7일·30일 증가량 | 오늘의 유효 전입자 수 − 7일·30일 전의 수 | `city_population_daily` → `growth_7d`, `growth_30d` |

세는 규칙은 설정 `growth.populationMode`로 고릅니다.

| 값 | 이름 | 세는 계정 |
|---|---|---|
| 1 (기본) | `linked` | 게스트가 아닌 로그인 수단이 붙은 계정 (`player_credentials.type <> 'guest'`) |
| 2 | `linked_or_proven` | 위 + 활동이 확인된 게스트: 레벨 `provenMinLevel`(3) 이상, 계정을 만든 지 `provenMinAccountDays`(3)일 이상, 활동한 날 `provenMinActiveDays`(2)일 이상 |

두 규칙 모두 **정지된 계정과 전입신고를 하지 않은 계정은 세지 않습니다.**

> **알아 둘 것.** 계정 연결(이메일·소셜 로그인) 기능은 아직 없습니다. 그래서 기본 규칙(`linked`)에서는 **모든 도시의 유효 전입자 수가 0**입니다. 지금 당장 숫자를 움직이게 하려면 관리자 화면에서 규칙을 `linked_or_proven`으로 바꾸거나, 계정 연결을 먼저 만들어야 합니다. 어느 쪽으로 갈지는 운영 결정이 필요합니다 ([DEVELOPMENT_PLAN](DEVELOPMENT_PLAN.md) 7장).

게임 화면의 "이사" 메뉴는 내 계정이 세어지고 있는지와, 아니라면 이유(`guest_account` / `not_proven`)를 보여 줍니다.

### 언제 다시 세는가

- 전입신고와 이사가 **커밋된 직후** 그 도시를 다시 셉니다 (`Growth::touch`). 집계가 실패해도 전입·이사는 되돌리지 않고, 다음 예약 작업이 바로잡습니다.
- 예약 작업(`bin/tick.php` → `CityOpsTick`)이 모든 도시를 점검해, 수가 달라졌거나 오늘의 기록(`city_population_daily`)이 없는 도시를 다시 셉니다. 계정 정지나 세는 규칙 변경처럼 전입·이사가 아닌 이유로 달라진 수는 여기에서 반영됩니다. 여러 번 돌아도 결과가 같습니다.
- 한 도시를 셀 때는 현황 행을 먼저 잠급니다. 같은 도시를 동시에 세는 요청은 줄을 서고, 마지막에 적힌 수가 가장 새로운 수입니다.
- 점검: `Growth::findInconsistency()`가 적힌 수와 지금 다시 센 수가 다른 도시를 찾아 예약 작업의 결과에 적습니다.

## 3. 이사

| 항목 | 기본값 | 설정 |
|---|---|---|
| 이사 가능 | 켜짐 | `growth.moveEnabled` |
| 수수료 | 1,000 GC | `growth.moveFeeGc` |
| 다시 이사할 수 있을 때까지 | 7일 | `growth.moveCooldownDays` |

`POST /residency/move`는 하나의 거래 안에서 다음을 모두 합니다.

1. 전입 상태·같은 도시 여부·기다리는 기간을 확인합니다. 협동 방어전에 참여하고 있는 동안에는 이사할 수 없습니다.
2. 수수료를 지갑에서 빼고 원장에 `residency_move` 사유로 적습니다 (잔액이 모자라면 여기서 거절).
3. `players.region_id`를 새 도시로 바꾸고 전입 일시를 새로 적습니다.
4. `regions.resident_count`를 이전 도시 −1, 새 도시 +1 합니다.
5. `city_residency_events`에 `move_out`, `move_in` 두 줄을 남깁니다.
6. 다른 도시를 지원하러 나가 있었다면 돌아옵니다.

커밋된 뒤 이전 도시와 새 도시를 **둘 다** 다시 셉니다. 같은 요청(`Idempotency-Key`)이 다시 오면 처음 응답을 그대로 돌려주고, 수수료를 또 받지 않습니다. 동시에 두 번 이사해도 한 번만 됩니다 (`tests/ConcurrencyTest.php`).

수수료는 도시 재정으로 가지 않고 사라집니다 (세금이 아닙니다). 이사한 뒤 초보자 보호의 "전입한 지 며칠" 기준은 **처음 전입한 날**부터 셉니다. 이사로 세금 면제 기간을 되살릴 수 없습니다.

## 4. 확장 단계

| 코드 | 이름 | 기준 인원 (기본) | 하는 일 |
|---|---|---|---|
| `landmark_review` | 상징물 제작 검토 | 100명 | 상징물 하나를 만들지 검토 |
| `street_candidate` | 상징거리 제작 후보 | 500명 | 상징거리 제작 후보로 올림 |
| `street_open` | 상징거리 개방 목표 | 1,000명 | **상징거리 모델링 기준 인원** (`opens_street = 1`) |
| `special_zone_review` | 추가 특화 구역 검토 | 3,000명 | 특화 구역을 더 만들지 검토 |

- 기준은 `city_growth_milestones`에 있고 관리자가 인원(1 ~ 10,000,000)·이름·설명·사용 여부를 고칩니다. 바꾼 값은 `config_history`와 감사 기록에 남습니다. 단계의 순서는 늘 인원이 적은 것부터입니다.
- 도시의 **확장 단계**(`stage`)는 닿은 기준의 수입니다.
- 도시마다 상징거리 기준 인원을 따로 둘 수 있습니다 (`city_population_stats.modeling_threshold`). 비어 있으면 공통 기준(`opens_street`인 단계의 인원)을 씁니다.
- 기준 인원을 바꾸면 모든 도시를 다시 확인합니다. 새 기준에 이미 닿아 있던 도시에는 알림이 생깁니다.
- 한 번 오른 단계와 한 번 달성한 상징거리 기준은 주민이 줄어도 내려가지 않습니다 (이미 제작이 시작되었을 수 있기 때문입니다). "다음 단계까지 몇 명"은 지금 인원으로 계산합니다.

## 5. 기준 도달 알림

도시가 기준에 닿으면 관리자 알림(`city_growth_notifications`, `kind = 'milestone'`)이 하나 생깁니다.

- **중복 방지:** `dedupe_key`(`milestone:<도시 번호>:<기준 번호>`)가 유일 키입니다. 같은 도시의 같은 기준에는 알림이 한 번만 생깁니다. 동시에 여러 요청이 같은 도시를 세어도 `INSERT IGNORE`라 하나만 남습니다.
- **모델링 진행 알림과 구분:** 제작 작업의 상태가 바뀔 때 생기는 알림은 `kind = 'modeling'`입니다. 관리자 화면은 두 종류를 따로 보여 줍니다.
- **처리:** `new` → `acknowledged`(확인) → `assigned`(담당자 배정) → `closed`. 알림을 확인한 관리자에게 담당을 배정할 수 있고, 알림에서 바로 제작 작업을 등록할 수 있습니다 (작업에 `notification_id`가 남습니다).

## 6. API

| 요청 | 내용 |
|---|---|
| `GET /cities/growth` | 모든 도시의 유효 전입자 수, 단계, 모델링 상태, 단계표, 세는 규칙 |
| `GET /cities/{code}/growth` | 한 도시의 상세: 누적, 7일·30일 증가량, 단계별 달성, 최근 추이 |
| `GET /residency` | 내 전입 상태, 세어지는지, 이사 조건 |
| `POST /residency/move` | 이사 (`Idempotency-Key` 필요) |

형식은 [API_SPEC](API_SPEC.md) 19장.

## 7. 관리자

"도시 성장 관리"와 "도시별 전입자 통계" ([ADMIN_SYSTEM](ADMIN_SYSTEM.md) 12장). 전국 도시별 전입자 수와 증가 추이, 기준 달성 도시, 모델링 미착수·진행 중·적용 완료 도시, 지역별 콘텐츠 개방 현황, 도시별 상세.

## 9. 남은 일

- 계정 연결 기능이 없어 기본 규칙에서는 수가 움직이지 않음 (2장).
- 클라이언트에 HTTP 구현이 없어 게임 화면은 모의 서버의 값을 보여 줌. 응답 형식은 표본으로 대조함 ([TEST_PLAN](TEST_PLAN.md) 15.4).
- 기준 인원, 수수료, 기다리는 기간은 플레이 데이터를 보고 다시 정해야 함.
